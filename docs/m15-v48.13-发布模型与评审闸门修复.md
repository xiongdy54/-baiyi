### 1.3 引擎怎么判的

`electron/mindmapEngine.js` `runReview` 末尾（修复前）：

```js
const status = issues.some((i) => i.type === "topic_list" || i.type === "hollow_parent" || i.severity === "high")
  ? "fail" : issues.length ? "review" : "pass";
```

- 无视模型返回的 `status`（模型说 pass，引擎不看）。
- `x72` 的 `type === "topic_list"` → 无条件 fail，**`severity:"low"` 被完全忽略**。

而评审提示词【纪律】第 1 条写的是：

> fail 仅用于明确缺陷（空洞父节点泛滥、纯主题列表）；**轻微问题用 review 并列 issues**；良好用 pass。

**结论：提示词与引擎实现互相矛盾。模型遵守了提示词，引擎否决了模型。**

## 2. P1 实施内容（已落地）

### 2.1 评审闸门：severity 才是闸门，type 只是描述标签

```js
const hasHigh = issues.some((i) => i && i.severity === "high");
const status = hasHigh || (modelFail && issues.length) ? "fail" : issues.length ? "review" : "pass";
```

- ① `severity === "high"` → fail（唯一标签无关的闸门，也是「高严重度结构缺陷」的唯一入口）；
- ② 模型**显式** `status=fail` 且给出 issue → still fail（**单向棘轮**：模型说 fail 不作废；模型说 pass 不能抵消 high）；
- ③ 其余有 issue → `review`（记录不阻断）；无 issue → pass；
- ④ **非阻断意见必须留痕**：`metrics.reviewStatus` / `metrics.reviewIssues` 随 run 账本落库（此前通过路径直接把 issues 丢弃，用户与后续局部修复都看不到）。

> 确定性完整性校验（JSON / nodeId 唯一 / parent 存在 / 无环 / span 合法 / 子 span ⊆ 父 span / 引文可逐字定位）**仍是独立硬门**，不因模型 `pass` 放行——这一层本就在评审之前。

### 2.2 Published / Candidate 发布模型

```js
const publishedElsewhere = !!(prevActive && prevActive.id !== reuseId);
const publishNow = statusOverride === "section_ready" ? !publishedElsewhere : !partial;
```

| 场景 | 行为 |
|---|---|
| 已有别处发布的版本 + 新的首层就绪 | 首层落库为**候选**（可查看、`is_active=0`），**不顶掉**已发布版本 |
| 无任何已发布版本 + 首个首层 | 作 **provisional 发布**（`run.status = section_ready` 可辨） |
| 候选续跑完成 | **事务性发布**：候选成为新的 active，旧版退位不删 |
| `partial`（预算触顶 / 调用失败） | 永不发布（保持旧行为：不伪装完整） |

run 输出新增 `published` / `candidate` / `heldByPublishedMapId` 留痕；`section_ready` 广播与返回值都带 `published`，
UI 必须如实区分「已发布」与「候选」。

### 2.3 广播契约自足（P2 地基）

- 所有进度广播（含此前遗漏的 `coverage_audit` / `expand` / `retry`）一律携带 `runId` / `documentId` / `title`；
- **终态也必须广播**：`failed` / `review_failed` / `cancelled`——此前失败只回给 IPC 调用方，用户离开工作区后完全不可见；
- 契约由 `tests/m15r.engine.test.cjs` E25（6 断言）锁定。

## 5. P4 增量深化与增量评审（已实施，D46）

用户拍板「改成增量评审」后实施。核心是**把「展开」与「深化」分开**：

| | 展开 | 深化 |
|---|---|---|
| 触发条件 | 节点**已有**子结构，只是折叠 | 节点**尚无**更深结构、且有 sourceSpans |
| 代价 | **零 AI 请求**（纯渲染层状态） | 1 次深挖（按分片数）+ 1 次增量评审 |
| 入口 | 画布折叠徽标 / 详情「展开子树」 | 详情「深化此节点」（仅可深化节点可见） |

### 5.1 增量深化 = 以已存地图为基底的作用域受限 generate

复用同一条管线、同一本账、同一套本地校验与评审机制，差异**只有五处**（代码内逐条标注）：

1. 以**已存结构**为基底装配（不重建 → 不跑 section、不依赖分片缓存，也不会丢掉原图里 merge/global 产出的上层节点）；
2. 深挖队列**只播种目标节点**；
3. 不跑覆盖审计/补漏（不为整份材料新增自动成本）；
4. 不跑 editorial 终编辑（整树润色按次点击重跑不划算；新子树仍走本地结构校验）；
5. 语义评审只覆盖本次新生成的分支 + 必要上下文。

**前置校验**（都不消耗调用）：地图版本存在 → 目标节点存在 → 目标**无子结构**（否则 `already_expanded`，展开不需要生成）→ 目标有 sourceSpans（否则 `no_scope`，无作用域无法定位证据）。

### 5.2 增量评审（本批的关键决定）

评审范围 = 目标节点 + 本次新生成的子孙 + 必要父/兄弟上下文；payload 明确声明「材料其余部分未改动、不在本次评审范围内」。
**结果只决定这一支能否发布**：单分支评审未通过时 run 停在确认、**地图行原封不动**、其余分支完全不受影响。

这是「按需深化」与「整树闸门」冲突的正解——深化的子树不可能先评审再展示，只能就地评这一支。整树评审仍用于初次生成。

### 5.3 原地发布

深化就地更新**同一版本行**（版本 id 不变 → 卡片溯源不断链），`isActive` 保持不变（**深化不改发布关系**）。

### 5.4 UI：把「没画出来」与「没有更深的内容」分清

- 可深化节点在画布上带 **＋号徽标**（与折叠 +N 同槽位，二者互斥：折叠要求有子节点），`<title>` 提示「尚无更深结构 · 可深化」；
- 节点详情：可深化 → 「深化此节点」按钮 + 说明；终态 → 明确写「已是终态（原子结构/纯过渡文字）」；
- 画布提示条同步说明两者区别。

### 5.5 已知代价（不粉饰）

深挖指纹 `expandFingerprint` 含 `depth`，而**首层图没有 global 根**、同一节点的 depth 比整图浅一层 →
深化用掉的深挖缓存与之后的全量重生成**不共享**，该分支会被重新分析。

取舍可接受（一次深化只花 1～2 次调用，换来「不必等整图跑完就能先看某一支」），已写进代码注释并由**特征化测试 E26⑦ 锁定**，避免将来静默变化。

## 6. P3 应用重启续跑（已实施，D47）

**核心修正：被打断 ≠ 失败。**

| | 旧行为 | 新行为 |
|---|---|---|
| 启动对账 | `running` → `failed_timeout`（关掉应用被记成一次超时失败） | `running` → **`interrupted`**（`error_code='interrupted'`，文案写明缓存保留、零重复计费） |
| 重启后 | 什么都看不到 | 指示器显示「**导图生成被中断 · 可继续**」 |
| 点击 | — | 打开导图并携带 `resumeRunId` → 收完原文即同 runId 续跑（已完成分片全部命中缓存） |

实现：
- `listResumableMaterialMapRuns()`：可续跑 = `interrupted`（被关闭打断）+ `section_ready`（首层就绪待续跑），连表带出材料标题；走 `mindmap:pendingRuns` IPC；
- 渲染层启动即 `seedFromRuns()` 播种指示器；点击时 `phase === "interrupted"` 才带 `resumeRunId`（**首层就绪不自动续跑**——按需深化由用户点具体节点决定，见 §5）；
- 只有**正在跑**的任务才显示「取消任务」（给已中断的 run 一个假动作没有意义）；
- 播种只接受 `interrupted` / `section_ready`，其余状态一律不播种：**宁可少提示，也不能把已完成的图显示成「被中断可继续」**（activity 测试 A6② 锁定）。

## 7. P5 真实运行审计与修复（D48）

用户重新生成《干掉∞人：优绩主义如何击败了所有人？》后追问三件事。库内只读审计（run `50074faf`）给出的现场：

| 阶段 | 时刻 | 耗时 |
|---|---|---|
| 首层 section ×2 | 20:55:57 → 20:56:35 | **73s（图 already 可看）** |
| 自动深挖 expand ×22 | 20:56:52 → 21:02:08 | **329s** |
| editorial | 21:02:42 | 34s |
| review | 21:03:08 | 26s |
| 合计 | 20:55:21 → 21:03:08 | **466.7s** |

其中 21:01:57 一次 `ECONNRESET`（3s）使整轮降级 `partial:call_failed`。库中**没有任何** cancelled 运行或 cancelled 调用。

### 7.1 「已取消」误显——P2 引入的真 bug

引擎除终态外还广播若干**子事件**：`expand`（每完成一个深挖作业一次）、`coverage_audit`、`retry`、`waiting_model`。
P2 首版把广播里的 `stage` 直接当成「阶段」存进任务状态 → `describeTask` 的 `default` 分支把运行中的任务显示成 **「已取消」**。
用户在一次完全正常的运行里看到两次「已取消」，正是这些子事件到达的时刻。

修：`normalizeStage()` 白名单（子事件 → `running`）；**未知事件沿用上一次状态，绝不编造**；`describeTask` 的 `default` 返回 `null` 兜底。

### 7.2 一次失败把可用成果作废

旧规则「`partial` → 不发布」在本轮更新的**正是当前已发布那一行**时（续跑 / 深化）会把用户手上已经能看的图置为未发布——
本次现场：73 节点成果在收尾瞬间变成 `is_active=0`，文档没有 active 版本。

修：**已发布的版本不因一次失败而消失**（`reuseIsPublished` → partial 也保持发布）；降级事实由 run 行 `completeness=partial:call_failed` 如实留痕。
反向仍严格：**尚未发布**的新版本 partial 时依旧不发布（不伪装完整）。

### 7.3 并发写同一行地图

主 run 还在续跑深挖时（20:58），用户点了某节点「深化」——两个 run 各自以不同基底装配、先后写**同一行**地图版本，
先完成的深挖成果被后收尾的主 run 覆盖（用户看到图忽大忽小）。

修：引擎级**同材料同范围串行化守卫**（`findRunningMaterialMapRun`）——已有未收敛 run 时拒绝再起一轮（`code: "busy"`，零调用）；
**同一 runId 续跑不算冲突**（否则续跑会被自己挡死）；已中断/已结束的运行不占闸门。UI 侧运行中禁用深化，但闸门在引擎，不靠 UI 自觉。

### 7.4 口径修正：首层就绪后不再自动深挖整树

首层 73 秒就已可用，自动深挖又跑了 393 秒，而用户以为图出来就该结束了。这与 D46 的口径（**初始只需足够深入，最深的枝条按需展开**）直接冲突。

改为：首层就绪即 `phase=done`，可看可操作；画布带＋号节点按需深化；想一次跑完的人用侧栏**显式**按钮「自动深挖全部（约 N 次调用）」——原能力保留，但不再默认发生。

### 7.5 指示器：打开即消失

点「打开导图」后（非运行中）本条提示即消失——用户已经去看图了，提示的使命结束。仍在运行的除外（那时用户要的是看得见的进度，而且续跑一旦开始会有新广播把它带回来）。

## 8. P6 空态自救与入口可见性（D49）

用户反馈三件事：上次的导图成果不见了、看不到历史版本、看不到「自动深挖全部」。

**先复现再修**：写了一个探针（启动真实应用 + 预置「某材料只有一个未激活版本」的库），
复现出与用户描述完全一致的现象：

```
{ isEmpty: true, versionSection: false, versionCount: 0, recoverHint: false, hasDeepenAllBtn: false }
```

### 8.1 历史版本区被两重条件挡住

它渲染在 `hasKey ? … : …` 分支**内部**，又嵌在 `phase === "done" && structure` **里面**。
于是「无 Key」或「没有已发布版本」时，用户看不到任何版本入口——这正是用户的处境
（P5② 那个 bug 把已发布版本置为未激活，用户重开工作区只看到「尚未生成」，以为 73 节点成果丢了）。

修：版本区**移出这两重条件**（它是纯只读操作），任何阶段、无 Key 都可见；空态且 versions 非空时明确写出
「当前没有已发布的版本，但历史里有 N 个——点下面任意一版即可激活查看（成果没有丢）」。

探针验证（修复后）：`versionCount: 1`、`recoverHint: true`，点击版本后 `emptyStill: false`、**画布渲染出节点**。

> 教训入档：上一轮我写下「历史版本里就有」时**没有验证**，那是错的。本轮改为先用探针复现，再把复现固化成 gui 断言。

### 8.2 「自动深挖全部」可见性条件过窄

此前只在 `phase === "done" && expandPlan && plannedCalls > 0`（＝刚跑完首层的那一瞬间）出现；
关掉工作区再进来、或打开一张旧图，按钮永远不出现。

修：改为按**当前图里可深化节点数**（无子结构 ∧ 有 sourceSpans）决定；按钮文案为「自动深挖全部（N 个可深化节点）」；
没有本轮 run 时也能直接走完整管线（section 同样命中缓存）。

### 8.3 版本行版面

用户反馈「标题所在的格子太小、标题文字很多挤在一起，删除按钮只有两个字空间却很大」。

重排：标题与时间拆成两行；标题撑满可用宽度、最多两行（`-webkit-line-clamp: 2`）+ `min-width: 0` 允许收缩；
删除按钮 `flex: none` 固定 44px，不参与拉伸。
