### 判红＝真实缺陷

**A-9 ·（中）优先级取值域双向错：合法值 0 被静默改成 50，非法值原样入库**
- `electron/db.js:1177`（insert）、`:1246`（update）、`:2090` 三处都是 `Number(card.priority) || 50`。
  `Number(0) || 50 → 50`，所以 **0 写不进去**；而 `updateCard` 也走同一表达式，
  于是「只改答案文案」也会把已经存在的低值顺手改掉（F36 M1b 实测）。
- 界面明写「优先级（0-100，越高越先复习）」（`src/components/Reader.tsx:2110`），
  §6.4 的 R14 又依赖「边缘 ≤30」这个低值区间 —— 0 是广告过的合法取值。
- **F36 M1d 的意外收获（同一处的反向问题）**：越界值**完全不钳**，实测
  `−5 → −5`、`9999 → 9999` 原样入库。也就是说这条写入口
  **把合法边界值改坏、却放行非法值**，两个方向都错。
- 对照 M1c 证明不是测试问题：`30 / 100 / 1` 三个值均原样落库。
- 修法方向：`Number.isFinite(n) ? clamp(n,0,100) : 50`（把 `||` 换成显式默认值判断）。

**A-10 ·（中）`ai_gen_batches` 只写不读 —— 已付费生成的草稿永久找不回**
- 全仓 `grep ai_gen_batches` 只有三处：建表（`db.js:154`）、`INSERT`（`:1698`）、`UPDATE status`（`:716`）
  加一次 `rowExists` 存在性校验。**没有任何 SELECT、没有 IPC handler、preload 也没出口。**
- F36 实测：`createAIGenBatch` 返回了 id、行确实带 `result_json` 落库（M2b 绿），
  但仓储层**取不到**（M2c/M2e 红）—— 用户关掉生成窗口后，那批已经花过钱的草稿在库里，
  界面上永远没有第二条路能拿回来。违反 §4.3-⑦ 与 §7.1.4。

**判红（1 条）**

**D-9 ·（低）`persist()` 失败后 `library.db.tmp` 残留，一次失败即让磁盘占用翻倍**
- `electron/db.js:683-692`：`persist()` 把整库写进 `dbFile + ".tmp"`，`try { writeSync; fsyncSync } finally { closeSync }`
  —— `finally` **只关 fd，不清 tmp**；随后的 `renameSync(tmp, dbFile)` 在注入失败时根本没执行。
- 实测 15/16 个函数在落盘失败后都留下一个 **528 384 B**（与当前库同尺寸）的 `library.db.tmp`。
- **有界**：下次 `openSync(tmp,"w")` 会截断重写，所以不会累积成很多份；但语义上是
  「**任何一次落盘失败都会让磁盘占用翻倍，直到下一次成功落盘**」，
  且在备份/杀软扫描/磁盘配额场景下多出一份**内容不完整**的库镜像，可能干扰恢复判断。
- 修法：`catch { try { fs.rmSync(tmp, { force: true }); } catch {} throw e; }`，或把清理并进 `finally`。

**七条判绿 —— 这部分同样重要，它把好几个「可能很糟」的猜测证伪了**

**A-14 ·（高 · 数据丢失）恢复动作自身会毁掉用户现有的库 —— `rmSync` 与 `renameSync` 两步非原子**
（第十二轮新增、第十三轮扩展到三处，**均已故障注入端到端复现**：`tests/fsrs/repro-restore-integrity.cjs`，纯 node、`os.tmpdir()` 沙箱）

`electron/backup.js:310-313` 换入 staged 库的写法是：

```js
if (fs.existsSync(stagedDb)) {
  fs.rmSync(p.dbFile, { force: true });      // ← 先把用户线上的 library.db 删掉
  fs.renameSync(stagedDb, p.dbFile);         // ← 再把备份挪进去；这两步不是原子的
  restored.push("library.db");
}
```

复现结果（R1 五条正向对照**全绿**：正常往返确实把库与 assets 都换回来了，所以 M2 的主路径是好的）：

```
✓ R1a~R1e 正常「备份→改数据→恢复→换入」往返完整（库内容回到 DB-V1、assets 一并复原）
     注入了一次 rename 失败；applyPendingRestore 抛错：EPERM (simulated: 杀软占用 / 跨设备 / 权限)
     恢复后线上 library.db 是否存在 = false
✗ R3a 【关键】换入失败不得让用户现有的库消失
✓ R3b 失败后标记保留（下次启动会重试）
```

**后果链**：`renameSync` 一旦失败（跨设备移动、杀软实时扫描占用、权限、磁盘抖动），
用户的 `library.db` **已经被删而新的还没进去**。
而 `main.js:1332-1336` 是 `try { backup.applyPendingRestore(); } catch { console.error(...) }`
**接一句 `await initDb()`** —— 于是应用带着一个**不存在的库文件**继续启动，
`initDb` 会建出一套空库，用户睁眼看到「所有的书和卡都没了」。

**缓解事实（必须一并写明，否则夸大）**：恢复前 `backup.js:273` 那份 `safety` 备份里
存着恢复前的完整状态，所以数据**并非不可找回** —— 但找回要求用户知道去解那个 zip，
界面在此过程中不给任何提示。所以这是「可手工恢复的静默数据破坏」，仍判高。

**修法**（顺序反过来即可，改动很小）：先把线上库改名让位，再换入，成功后才删让位的文件 ——
```js
const backupAside = p.dbFile + ".pre-restore";
fs.renameSync(p.dbFile, backupAside);        // 原子让位，失败则原样未动
fs.renameSync(stagedDb, p.dbFile);           // 换入
fs.rmSync(backupAside, { force: true });     // 只有换入成功才清理
```
让位失败就整个中止，用户数据分毫未动。

**第十三轮：A-14 不是孤例 —— 同一个非原子写法在三处，全部注入验证通过**
（`tests/fsrs/repro-restore-integrity.cjs` 扩展后重跑，12 条断言：6 绿 6 红）

`fs.rmSync(线上) → fs.renameSync(staged→线上)` 这个写法在 `applyPendingRestore` 里出现**三次**：
`:311` library.db、`:317` assets、`:324` memory。逐个注入一次 rename 失败：

```
✓ R1a~R1f 正常往返全绿：库、assets、memory 树都正确换回   ← 主路径确实是好的
✗ R-db      换入失败后线上 library.db 还在吗 = false
✗ R-assets  换入失败后线上 assets.png 还在吗 = false
✗ R-memory  换入失败后线上 memory\core.md 还在吗 = false
```

**第三处最要命**：`memory/` 按 §4.18-2 是用户记忆的**唯一真源**（不在主库里，靠 M2 显式打包）。
它同样被这对手柄保护 —— 一次 EPERM 就把用户全部记忆文件清空，而备份版还没换进去。

**R6 的部分失败比预想更糟**。我原本担心的是「库来自备份 + 资源仍是新数据」的错配，实测：

```
[R6] db 换入成功、assets 换入失败后：library.db=DB-V1 / assets/a.png=(缺失)
✓ R6a 未出现错配态
✗ R6b 用户较新的那份 assets 已被删空
```

也就是说结果不是「错配」而是**更彻底的形态**：库回到了备份版本，
而 assets 目录被 `rmSync` 清空且没能换回任何东西 ——
**一本书的库记录指向一堆已经不存在的图片**，比错配更难诊断。

**结论与修法**（三处同一改法，成本极低）：把「先删后挪」换成「先让位、再换入、成功才清理」——

```js
const aside = target + ".pre-restore";
fs.renameSync(target, aside);        // 原子让位；失败则原样未动，直接中止
fs.renameSync(staged, target);       // 换入
fs.rmSync(aside, { force: true });   // 只有换入成功才清理
```

并且 `applyPendingRestore` 应当**整体事务化**：任一处失败就回滚已完成的那几处，
而不是留下「库已换、资源被清空」的半套状态。
