## 0. 为什么要另开一套，而不是再补既有套件

`tests/` 下已有 25+ 套件（m1…m15、k1/k2a/k2b、fsrs 六件套、undo、persist、backup、reader/pdf kernel、18 个 CDP GUI 套件）。
它们的组织方式是**按模块纵向**：一个里程碑一套，断言集中在该模块自己的输入输出。

指南里最难验证的东西恰恰是**跨模块**的：

- §7.2 数据完整性规则讲的是「任何一次写入都不许破坏其他表的事实」；
- §7.1.4 的完工标准是「启动 → 该单元主流程 → 重启不丢数据」这条**旅程**；
- §4.2-20 要求复习队列、统计仪表盘、卡片浏览页三处**同一口径**；
- §6.6/§4.18/§4.19 三处重复声明「A 功能绝不写 B 表」。

纵向套件验证不了这些，因为它的快照边界就是它自己的模块。
所以这套流程测试**按用户旅程 + 跨模块不变量横向组织**，并且一律用
`sql.js` 只读打开**落盘后的 library.db**做表级审计（`lib/dbenv.cjs`）——
不看函数返回值，看磁盘上真正发生了什么。这同时覆盖了「落库即落盘」（§7.2 L874）这一条从未被正向验证过的承诺。

## 2. 每条流程的设计细节

### F03 复习调度与数据守恒（已落地）

分节与判据：

1. **S1 冷启动 schema**：27 张表实际存在；`cards.sibling_key`、`review_logs` 六个 v23 快照列齐备；`cfg-default` 恰好 1 行、权重长度 21（§7.4 L900）。
2. **S2 八字段往返**：`fsrs_json` 必须原样存回 `{state,due,lapses,stability,difficulty,reps,lastReview,learningSteps}`——§7.1.7 明令「文档声明的字段不允许实现时静默裁剪」；并核对日志 `fsrs_after_json` 与卡表 `fsrs_json` 两处一致。
3. **S3 写库即时落盘矩阵**（本次新发现所在）：对 13 个写库函数逐个「先刷盘建立基线 → 执行 → 只读盘比对」。
   只有 `insertFsrsConfig` 未通过；`createKnowledgePoint`/`createJournalEntry` 等全部通过。
   另含 §7.2 唯一例外的**双向**验证：`saveJournalDraft` 不得立即产生正式条目，`sendJournalDraft` 必须产生。
4. **S4 同源延后**：一次 `computeTodayQueue()` 前后对 11 张业务表做全量快照差 → 必须零差异（「延后是队列视图而非调度写入」）；组内当日只放行 1 张、其余显式进 `deferred` 且带可读原因；评分后额度耗尽、撤销后额度回收；learning 卡与挂起卡豁免。
5. **S5 统计同口径**：`kpi.dueToday + kpi.siblingDeferred` 必须等于我从原始表逐行数出的「活跃且 due ≤ 今日 24 点」总数——这是 §4.2-20「不静默少卡」的可执行形式。
6. **S6 跳过与撤销账目**：跳过只动 `review_skips`（`cards`/`review_logs` 零变化）；两评两日志；后评先撤（按 `review_seq` 而非 `id`/`reviewed_at`）；撤销后八字段含 `learningSteps` 完全复原、日志被物理删除；卡被外部改写后拒绝撤销。
7. **S7 参数环境不可变**：同权重两次插入 → 同一 `config_id`；切换只移动指针、`cards` 表逐行字节不变；配置表净增恰 1 行；悬空指针回退 `cfg-default`。
8. **S8 软删除**：删除后行仍在且 `is_deleted=1`、业务查询不再返回、该卡 open issue 自动收口。
9. **S9 重启**：清理残留 `.tmp`；二次 `initDb`（重 require，等价于重启进程）后卡集合、日志数、配置数全部不变。
10. **S10 优化权重应用后重启**：见缺陷 D-TEST-01。

每轮随机量：同源组规模、卡优先级、权重扰动、种子 → 长跑中覆盖不同组合；seed 打进结果 JSON，失败可复现。

### F05 备份—恢复—升级生命周期（已落地）

角度：其他流程验证「这一刻正确」，这条验证「数据活得比这次会话久」。
1. 播种一份真实形状的数据（粘贴书 + 摘录 + 卡 + 复习日志 + 日记 + 设置 + 手工放一个 memory 文件树与 asset 文件）。
2. `createBackup` → 用 jszip 解包核对清单：必须含 `library.db`、`settings.json`、`assets/**`、`memory/**`、`backup-meta.json`；**绝不含** `ai-config.json`（§7.6 L919 禁区、§4.18 L396 遥测同禁区）。
3. 破坏现场（删库、删 memory、改 settings）→ `restoreBackup` + `applyPendingRestore` → 重新 `initDb` → 表级快照必须与备份前逐行一致。
4. 路径穿越：手工构造含 `../evil.txt` 的 zip → 恢复必须拒绝且不在 userData 之外落文件。
5. 升级：备份前安全备份必须存在（`label=safety`）；恢复失败时现场不被破坏。
6. 旧库形态迁移：把当前库的 v23 列删掉 + 造几条 v22 形态日志（无快照列）→ 二次 `initDb` → 列被补齐、`review_seq` 由 rowid 回填且稠密单调、旧日志被判定为**不可撤销**（§4.4.9 L172）、`cfg-default` 只播种一次。

### F06 AI 制卡契约与闸门（node，离线可证）

不联网也能验的契约，全部来自指南 §6.3 与 §7.4：
scope 白名单封闭（11 个制卡族 scope，不多不少）；版本号播种只增不改、`card-vocab` 故意留 v1；
CardLint 规则表 L1–L16 **无 L15**（同日删除，L585）；error 阻断落库、warn 可接受、info 仅提示；

R20 记忆接地只允许 `situationRequired` 的 scope；AI 永不写 `fsrs_json`/`review_logs`/LKM 证据表。

### F07 用户记忆与隐私边界

`memory.enabled` 默认关；关闭时零请求零注入但文件保留；整理只追加/合并/标记，绝不整文件重写，
`<!-- 用户手写区 -->` 逐字不动；`index.md` 由系统重生成；core ≤800 / index ≤1200 / topic ≤1200 字符；
注入超预算时**从后往前**按接地顺序裁剪；`memoryRef` 必须是注入块的逐字子串，否则标「情境来源存疑」且默认不勾选；
备份必须含 `memory/`，遥测/出错上传白名单永不含其内容。

### F33 落盘往返保真（第 33 条）

F04 管「写一半崩了怎么办」，F05 管「备份能不能恢复」，F10 管「反复落盘行不变」，

### F32 写入口存在性矩阵与假成功清点（第 32 条）

F19 把所有**读**入口当对手喂垃圾参数，F15 测「同一个写入口做两遍」，这条补上矩阵缺的第三角：
**写入口打在不存在的行上会发生什么**。两种失败方式都值得机器盯着：

  同时「假成功候选总数 ≤ 18」做成棘轮，只许降不许升。
- **越界改写**：本该只动一行的 UPDATE 条件写松了，动到别人的行。这种破损在正向旅程里永远不显形。

### F31 全库不变量体检（第 31 条）

前 30 条都是「沿着一条功能线往里看」，这条把方向掉过来：走完一段真实旅程（导入 → 摘录 → 6 张卡 → 6 次评分 →
日记 → 阅读事件 → issue → 图片资源 → 暂停），然后把 `library.db` 整张当**一张图**来体检。

关键设计有三点：

1. **不写死表清单**。运行时从 `sqlite_master` + `PRAGMA table_info` 读表和列，凡是点名的 `*_id` 引用列
   一律反查父表。这样产品加了新表/新引用列，这条会自动扫到，而不是默默漏掉。实测扫到 14 处跨表引用、
   46 个时间戳列、17 张带软删位的业务表。
2. **多态引用单独建模**。`extracts.parent_id` 的父表由兄弟列 `parent_type` 决定（`extract`→extracts、
   `document`→documents）。第一版把它当 `library_items` 反查，立刻报出一个**假**悬空——这正是这条流程
   最有价值的地方：它把「约定维护、sql.js 没开 FK」的引用面暴露出来，也逼测试作者去读实现。
   现在按 `parent_type` 分发，并且**遇到未点名的 parent_type 取值就报警**（将来悄悄加一种类型会先被这里看见）。
3. **判红口径与既定决策对齐**。「父行根本不存在」= 真破损，判红；「父行存在但已软删」= §6.2 既定决策
   （删书时卡与摘录留在原地），只记录不判红；唯一例外是 `assets`——材料字节该随书走，挂在已登记的
   D-TEST-18 上。`deleteCard` 则相反，它承诺把自己卡上的 open issue 置为 `dismissed`，
   这条同时正反两面断言：被删卡的 issue 必须 dismissed×1，**没被删的卡的 issue 必须仍是 open**（收口不得越界）。

顺带纠正了两处「看起来像缺陷、其实是测试自己写错」的地方：`getDocument()` 返回的是 `documentId` 而不是 `id`
（第一版取 `doc.id` 拿到 undefined，被 sql.js 以「bind unknown type」拒绝）；`users` 出厂就有 1 行不是野值，
而是所有业务行 `user_id='local-user'` 的落点，于是改成显式白名单 + 两条正向断言（恰好 1 行、id 就是 local-user）。

结论：**21/23 通过，2 条为已知缺陷**——D-TEST-18（assets 不随书软删）与新登记的 D-TEST-23
（阅读字数取数不过滤已删书；今天被 D-TEST-12 的「图恒为 0」遮蔽，修好那张图就会开始计脏账）。

## 4. 长跑执行策略

- 编排器：`node tests/flows/run.cjs --hours H --gap S [--only F03] [--allow-gui]`；
  每轮重扫目录 → 新流程自动加入。
- 结果留痕：`tests/flows/results/`（`soak.log` 人读、`history.jsonl` 机读、`soak-state.json` 累计计数、
  `failures/<ID>-c<N>.log` 完整输出）。
- **单实例锁** `soak.lock`：两条流程共用同一沙箱目录会互删文件、制造假失败（本次实测踩过，已修）。
- 沙箱位置：系统临时目录 `os.tmpdir()/incremental-reading-flows/`。不放 `tests/tmp-*`——
  那里会被其他会话/脚本按通配清理（本次实测被删过一次）。
- 判据收紧：零断言 = 失败；崩溃 = 失败；**已登记缺陷意外转绿 = 失败**（提示撤销登记，防止缺陷标记腐烂）。
- 外部干扰：检测到进程被信号杀死或零断言早退时自动重试一次；真实断言失败绝不重试。
- GUI 流程默认关闭：既有 harness 会 `taskkill /IM electron.exe /F`，那会杀掉用户正在使用的应用；
  长跑期间不触碰用户的应用实例。需要跑 GUI 流程时显式 `--allow-gui`，并逐条人工在场确认。
- 性能流程（F10）测量期间不要并发跑重活：本次实测在同一台机器上并发跑 16 个既有套件，
  把当轮 F10 从 3 秒拖到 6 分钟（未失败，但耗时读数被污染、编排器看起来像「卡住」）。
  结论：F10 的数字只在无并发负载时可信，报告里的性能趋势要按此剔除污染轮。
- 同一 label 的沙箱目录会被两个进程共用，后起的一方 `freshDir()` 直接把前一方正在写的库抹掉
  （实测：手工调试 F10 时出现「卡全部入库」三处假红）。为此 harness 支持
  `FLOW_INSTANCE=manual` 环境变量，给沙箱目录加后缀隔离——**手工跑任何一条流程都要带上它**，
  长跑不带（保持目录名稳定便于事后查看）。
- 长跑期间 F10 出现过 2 次崩溃形如 `ENOENT: rename library.db.tmp -> library.db`。归因已查实：
  是**我自己没带 `FLOW_INSTANCE` 的手工 F10 运行**（21:40:19 与 21:40:24）与长跑撞进同一个沙箱目录，
  后起一方 `freshDir()` 把前一方正在 rename 的 tmp 抹掉——不是外部第三方进程，也不是产品竞态。
  时间线证据：两次异常紧邻，且第二次的开始时刻正好等于第一次的结束时刻。
  加上 21:42 的沙箱隔离之后，F10 又跑了 88 轮，此类崩溃零复现。
  遗留一条改进项：编排器的重试只识别信号级被杀，识别不了这种抛错，所以它会留在崩溃计数里。
