结构主线：谁能写库、谁能出网

四道泳道一条纪律：渲染层拿不到文件与网络，写入收在 db.js 一处，出网收在主进程三处。蓝框＝产品运行时，灰框＝不随产品发布的工具，虚线＝契约存在但生产未接线。

写纪律

一处写，全量落

  • library.db 的 persist() 共 64 个调用点全部在 db.js 内；文件注释即写明业务码不得绕过仓储层。
  • 因为是内存库 + 全量回写，运行期被外部脚本改动的 library.db 会被下一次落盘整体覆盖 —— 所以恢复只能"重启时换入"。
  • dictionary.db 分库不是整洁性偏好，是为了让 340 万行词条不抬高主库的每次写成本。
  • 第二真源在库里看不见：userData/memory/ 是 Markdown 文件树，契约要求永不整文件重写。

边界纪律

渲染层是纯客户端

  • nodeIntegration:false + contextIsolation:true；出网与读文件在结构上不可能发生在渲染层。
  • 实测 src/ 内零处 require / node: / ipcRenderer。跨进程只经 23 个 window.*API ↔ 159 个 handler。
  • 捕捉窗连 cards / library / ai 都拿不到 —— 它是能力子集，不是缩小版主窗口。
  • 读本地文件走两条自定义 scheme（bookasset: / pdfres:），且必须在 app ready 前注册，否则封面图与 pdf 字形会永久失败。

容易改错的地方

图上看不见的契约

  • FSRS 有三份实现：渲染层调度用 ts-fsrs，主进程优化用 fsrs-rs-nodejs，fsrsTime.js 是手工复刻且绝不 import 前者。三者无代码依赖，只靠版本锁定与 S7/L6-A 断言维持一致。
  • kpScopes.js 的出层契约校验在生产侧零 require，真实消费方是测试台与测试。卡片与归一的确定性护栏已生效，出层 schema 校验尚未接入主进程。
  • 深色模式下自定义强调色必须写 body：深色档声明在 body.theme-dark，胜过从 :root 继承的值。
  • capSvc 的 db 是注入的 ctx，不走 require —— 按 require 图估它的影响面会偏小。
