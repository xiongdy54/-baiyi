## 0. 一句话

> **AI 的输入粒度必须随导图结构变细而变细：每个节点深挖时只读它自己的 `sourceSpans`，永不重读父级原文。**

审计实测的当前形态是反过来的——「整本书 → 请从整本书里找 A → 整本书 → 请从整本书里找 A1」。修掉这一点同时解决**正确性**与**性能**两个问题；批量、并行、换模型都排在其后。

## 1. 目标与非目标

**目标**

1. 每个节点的深挖输入 = 它自己的原文片段（多区间），而不是父级覆盖范围。
2. 覆盖完整可核算：父节点的文本被其子结构覆盖了多少、剩余多少，可度量、可补漏。
3. 任何情况下**不丢原文、不截断结构**——只允许「按边界拆分」与「降级重试」。
4. 成本与进度**可观测、可复算**：以调用日志为真源，不以 run 计数为准。
5. 首层完成后**立即可看**，深挖按预算分层推进，可中断、可续跑、状态诚实。

**非目标**

- 不改渲染与布局算法（除 §3.10 的视口稳定规则）；
- 不改制卡链路（`card-structure` 等）；
- 不换模型、不做多模型路由（本方案与模型无关，只与「喂什么」有关）；
- 不做「一分钟级」性能承诺（见 §5.6）。

## 2. 概念与数据结构

### 2.1 坐标系统（先钉死单位，这是所有区间运算的地基）

```
canonicalLinearizedText = units.join(LINEARIZATION_SEPARATOR)   // 现有实现为 "\n"
canonicalDocOffset      = UTF-16 code unit offset               // 与 String.prototype.slice 语义严格一致
unitBase[i]             = Σ_{j<i} ( units[j].length + LINEARIZATION_SEPARATOR.length )
```

硬规则：

1. **坐标单位是 UTF-16 code unit**，不是字节、不是码点、不是「字符数」。CJK 之外必须覆盖 surrogate pair（emoji 等）与 combining marks；测试断言 `canonicalLinearizedText.slice(span.start, span.end)` 逐字等于期望文本。
2. `LINEARIZATION_SEPARATOR` 与拼接策略是**版本化常量**：`LINEARIZATION_VERSION`。
3. `sourceRevisionHash = sha256(canonicalLinearizedText + "|" + LINEARIZATION_VERSION + "|" + unitOrder.join(","))`——改分隔符或单元顺序即**显式**全体失效，不会静默错位。
4. 本文档之后出现的「区间/span」一律指 `[start, end)` 的 `canonicalDocOffset` 区间。

> 现有 `core.buildExtractionModel` 用的是**单元下标区间**（`nodeRange: [startUnit, endUnit)`），粒度太粗（本书整本 = 1 个单元）。v48.11 在其之上增加一层**字符级坐标系**，两者共存：单元下标继续用于 TOC 归属/粒度裁剪，字符级用于 span 与覆盖核算。

### 2.2 节点字段

```js
node.sourceSpans   = [{ start, end }, ...]   // 本节点自己的原文作用域；升序、不重叠、已合并
node.unitAnchors   = unique(包含这些 span 的单元锚)  // 派生量：证据定位 / remap / sourceRevisionHash 语义不变
node.residualSpans = []                       // 派生量：本节点覆盖 − ⋃直接子节点覆盖（不落库为真源，见 §3.2）
node.spanStats     = { spanChars, spanCount, gapFillRounds, dedupeHits, hardSplits }
```

**关键分离**：`unitAnchors` 继续承担「本节点的证据可以落在哪些单元」；`sourceSpans` 只承担「深挖时该读哪段原文」。当前 bug 的根源正是这两个语义共用了一个字段。

### 2.3 任务类型（队列元素）

| 类型 | 输入 | 产出 |
|---|---|---|
| `section` | 一个 section 组的原文分片（≤ 单片上限） | 该片的首层子结构 |
| `expand` | **节点自己的一个 span shard** | 该 span 内的子结构 |
| `gapfill` | **父节点的残余区段**（`residualSpans` 的一个 shard） | 该区段内的结构（或判定为过渡文本） |
| `merge` / `global` / `editorial` / `review` | 同现状 | 同现状 |

`gapfill` 是新增的第三类结构生成任务，专门接住「深层好看但覆盖是假的」这种失败模式（本轮补充约束之一，见 §3.2）。

### 2.4 枚举扩展

```
stopReason += "output_overflow" | "coverage_gap" | "scope_conflict" | "budget_exhausted"
run.status  = pending | estimating | section_ready | processing | partial | completed
              | failed_network | failed_timeout | failed_json | failed_validation | failed_rate_limit | cancelled
call.outcome = completed | failed | unknown_outcome          // 见 §3.7
```

## 3. 机制规则

### 3.1 span 推导（evidence → sourceSpans）

纯函数 `deriveSourceSpans(node, ctx)`，零 AI 决策：

```
① 候选：对本节点每条 direct evidence 调 core.locateEvidence(单元文本, quote, startOffset)
        → (unitAnchor, matchStart, matchEnd) → 换算成 canonical span
        （locateEvidence 与命中数裁决**已存在**于 core，且校验器已在为每条证据算这两个偏移）
② 聚类：候选区间升序后，间隔 ≤ CLUSTER_GAP（初值 400 code unit）的合并为一簇
③ 扩边：每簇向两侧扩展到最近的段落/块边界（`splitByParagraphs` 的同一套边界定义），
        单簇扩边上限 CONTEXT_CAP（初值 1,500 code unit/侧）
④ 钳制：与父节点 `sourceSpans` 求交；交集为空 → 该簇丢弃并记 `scopeConflict`
⑤ 合并：相邻/重叠区间合并，排序
⑥ 预算：见 §3.3（超限是**拆分**，不是裁剪）
```

**限定（本轮补充约束）**：evidence 是**锚点**，不是作用域的完整定义。§3.2 的覆盖账负责补足 evidence 未覆盖的语义区段，不允许「有 evidence 的区间才算这个节点的原文」成为隐含假设。

### 3.2 覆盖账与 gap-fill（防重复、防假深度）

```
residualSpans(parent) = parent.sourceSpans − ⋃ children.sourceSpans     // 区间差，已有 core.subtractRanges
```

- 残余比例小（初值：单段 < 800 code unit 或 < 父级 15%）→ 视为连接性/过渡文本，记 `residual: "transitional"`。
- 残余比例大 → 记 `coverageGap`，并把该残余区段作为 `gapfill` 任务入队：输入只有这一段，指令是「判断这段是过渡文字，还是遗漏的结构」。
- **reconcile 规则（必须）**：`sourceSpans` 与 `residualSpans` **都不作为存储真相**，而是每次结构变更后由纯函数重算（section → 每个 expand 作业完成后 → gapfill 完成后 → merge 前）。gapfill 产出的子结构其 span **立即并入父覆盖**并参与下一轮残余计算——否则同一区段会被反复认作 gap、反复请求。
- **两道防重门**：① gapfill 的缓存键包含残余区段签名（同样的残余 = 缓存命中，不再请求）；② 同一区段 gapfill 轮次上限 `GAP_FILL_MAX_ROUNDS`（初值 2），超限记 `coverage_gap` 留痕并停止。
- **覆盖度量口径**：一律用 canonical 区间的并集长度，**禁止用节点标题/文本长度累加**。

### 3.3 切分阶梯（只切不删）

任何超限输入按以下阶梯切分为多个 shard，**分别调用 + 本地合并**：

```
段落边界 → 句边界（。！？；!?;…）→ 硬切（极端情况）
```

- 上限约束的是**单次 request payload**，不是材料的有效覆盖范围。**禁止**「取前 N 字丢掉其余」。
- **硬切时相邻 shard 保留重叠窗口** `HARD_SPLIT_OVERLAP`（初值 200 code unit），使跨边界的结构至少被某一片完整看到；重叠区产生的重复结构在合并时**按 canonical span 去重**（相同或被包含的 span 合并为一，`dedupeHits` 计数）。
- 硬切与降级次数入 `spanStats`，作为 benchmark 的观测项。
- 单片上限 `MAX_PAYLOAD_CHARS` 初值 6,000，由 benchmark 校准（见 §6）。

### 3.4 输出上限与降级阶梯（禁止截断）

```
触发 OUTPUT_OVERFLOW 的条件（三者任一）：
  finish_reason === "length"
  OR 解析出的节点数 > maxNodes(depth)
  OR completionTokens > MAX_OUTPUT_TOKENS
maxNodes: depth=1 → 8 | depth=2 → 25 | depth=3 → 60      MAX_OUTPUT_TOKENS 初值 12,000（按实测中位 ≈8 千留余量）
```

- **禁止截断 JSON**。半截产物只作 debug artifact 落盘留痕，**未经完整 schema + 证据校验不得进入 active map**（「图先于图示」）。
- 降级阶梯（确定性顺序）：**降低递归深度重试** → **拆分 source scope 后分片重试** → 仍溢出则标 `stopReason = "output_overflow"`、保留为待续跑任务，run 记 `partial`。
- `finish_reason` 必须在传输层被捕获并落库（当前被完全丢弃，见审计 §8）。

### 3.5 队列、排序与 run 级预算

- **预算统一为 run 级**：`section / expand / gapfill / merge / global / editorial / review` 全部计入 `usedCalls`；触顶 → `budget_exhausted` → run = `partial`（存未激活版本，旧 active 保持）。当前「只约束 expand + 三处死代码分支」的做法废除。
- **队列排序**：① 先按深度分层（BFS，保证可见地图均匀生长）；② **同层内 gapfill 优先于更深层 expand**（覆盖完整性优先于深度）；③ 层内按文档序（`sourceSpans.start` 升序），保证可复现。
- 计价：`estimatedCost`（按 preview 口径）与 `actualCost`（按 usage）分开累计，两者都可随时读取。

### 3.6 并行与自适应降级

- 可并行的独立单元：同组 section 分片、不同节点的 expand/gapfill 作业、同深度 merge 兄弟、review 分片。**同一节点的分片串行**（保持上下文顺序）。
- **并发阶梯（固定顺序）**：先落地 429/5xx 重试与失败隔离 → `concurrency = 1` 跑通基线 → 2 → 3 → 4 逐级验证。
- **遇 429**：`concurrency = max(1, floor(concurrency / 2))`，并进入**冷却窗口**（初值 60 秒内不再上调）；连续 N 个（初值 3）成功窗口无 429 才逐步恢复，避免 4→2→4→2 震荡。退避优先遵循 `Retry-After`，否则指数退避 + jitter。
- **单请求失败不得杀死整批**：作业级隔离，失败的作业标 `failed` 并留待续跑，不影响同批其他作业。
- 取消语义需从「每 run 一个 AbortController」改为「每 run 一组控制器」，取消时置位 + 逐组 abort。

### 3.7 重试、unknown_outcome 与重复计费

- 每次尝试落：`attemptId / requestId / retryOf / retryCount / outcome / wallMs / ttftMs / promptTokens / completionTokens / finishReason`。
- **流已开始后**的 timeout 一律记 `unknown_outcome`（服务端可能已生成并计费）→ **不盲目重试**；只在「未收到响应头 / 429 / 5xx / 连接错误」时重试。
- provider 若支持 idempotency key 则使用；不支持则如实记录 `unknown_outcome` 并在 run 总账里单列。
- 120 秒无数据超时保留；8 分钟墙钟看门狗保留，但**必须能区分**「用户取消」与「看门狗超时」——传输层的 abort 处理需还原 `signal.reason`，不能硬编码成 `已取消`。

### 3.8 可观测性（P0，必须与 §3.1 同批落地）

| 项 | 要求 |
|---|---|
| 调用日志 | 新表 `material_map_calls`（run_id, job 类型, node/span 键, 时间戳, 尝试次数, outcome, token, finish_reason, retry_of）——**分片表是缓存，调用日志是账** |
| Run 总账 | 每次运行结束写：`plannedCalls / requestedCalls / cacheHits / retries / successful / failed / cancelled / unknownOutcome / inputTokens / outputTokens / actualCost / validNodes / invalidNodes / evidenceCoverage / coverageGapChars / maxDepth / status` |
| 僵尸对账 | 启动时把 `status=running/processing` 且超过阈值的 run 收敛为 `failed_timeout`（或恢复为可续跑的 `processing`，见 §3.10） |
| usage | 请求体增加 `stream_options: {include_usage: true}`；无 usage 时明确标注「估算」 |
| finish_reason | 必须捕获并落库（§3.4 的溢出判定依赖它） |
| 计数器拆分 | `expandPlanned / expandCacheHit / expandRequested / expandSucceeded / expandFailed`，废除「缓存命中计入 expandCalls」 |
| 修复调用 | JSON 修复请求计入 `requestedCalls` 与费用 |
| 状态诚实 | `partial` 在 UI 显示为「部分完成，部分细节未展开」，不得显示为失败 |

### 3.9 Preview 两阶段与口径

**阶段 A（首次请求前）**

```
材料：…    范围：整份材料
待发送原文：129,887 字（精确）
首层结构分析：17 次（精确）
深挖：动态——按首层结构决定，上限 = 预算 150
预计费用：¥A ～ ¥B（区间）
```

**阶段 B（首层完成后、进入深挖前）**

```
首层已完成：发现 N 个可深挖节点
计划调用：N 次（第 1 层，精确）    缓存命中：M    需发送：N−M
预计新增 token：…    剩余预算：…    累计费用：…
[继续详细展开]  [就此停止]
```

**口径（本轮补充约束）**：所谓「精确」= **planned requests**。运行中另显「实际尝试 X」（重试、JSON 修复、溢出降级、分片拆分都会追加尝试），两类计数都进 run 总账。**不得声称首次请求前就能精确知道深挖调用量**（第 2 层以后依赖模型产出）。阶段 A/B 与实际发送继续共用同一 payload builder（§4.19-8 契约不变）。

### 3.10 阶段化与后台深挖

- **状态机**：`section_ready`（首层完成，已落一版可看的图，**status 不是 completed**）→ `processing`（后台深挖）→ `completed`（预算内跑完且覆盖达阈）或 `partial`（预算/溢出/残余未补完）。
- **原子落库**：每次增量重新生成结构 JSON 并在**一个事务**内写版本；禁止用户看到半棵树。
- **节点 id 稳定**：增量新增节点不得改变既有节点 id（按 span + 标题 + 父链匹配复用），否则选中态、卡片 remap 链、视口都会被打断。
- **视口语义**：首次完成允许自动 `fitView`；后台增量**保持当前 camera/transform**，仅在用户点「适应窗口」时重新适配。
- **进度文案**：只允许可计算口径——「已完成 37 个结构单元，仍有分支在展开」；**禁止虚假百分比**（expand 任务总量是动态的）。
- **重启恢复**：分片缓存已持久；`processing` 状态的 run 在启动时**不自动重跑**，仅提示「上次的详细结构未完成，是否继续？」（继续 = 从缓存续，零重复计费）。

### 3.11 缓存与版本

- expand/gapfill 的缓存键增加 `spanHash`（`sha256(排序后的 span 列表)`），保证「同一片段 + 同一标题 + 同一深度」复用、片段变了立即失效。
- `GENERATOR_VERSION` 与 `EXPAND_VARIANT` / `SPAN_MODEL_VERSION` **分离**：作用域模型升级只失效 expand 侧，**section 侧缓存继续可用**（本书重跑可直接省下 17 次调用 / 约 10 分钟）。
- 删除 `.unitAnchors` 作为深挖输入的一切路径（`mindmapEngine.js:675`），并修掉分片锚标签写死 `g.units[0]` 的问题（`:233`）。

## 4. ChatGPT 十四问逐条答复

| # | 问题 | 答复（机制见 §） |
|---|---|---|
| 1 | 修复后 12–15 万字预计多少 source analysis request？ | **首层不变，仍是 17 次**（`ceil(字符 ÷ 8,000)` 按组。首层没有 span 可依，必须读原文）。变的是深挖：从「每节点 17 次」降到「每节点 1–2 次」。完整量级见 §5。 |
| 2 | 每个节点如何确定 sourceScope？数据结构？ | §2.2 `sourceSpans = [{start,end},…]`（canonicalDocOffset / UTF-16 code unit）；推导见 §3.1 六步纯函数。 |
| 3 | 是否允许多 canonical ranges？ | **是**，`sourceSpans` 本身就是区间数组；覆盖/残余一律用区间并集运算（`core.subtractRanges` 已具备）。作者在远处回头补充某观点时，该节点自然持有多个不相邻区间。 |
| 4 | evidence 如何确定性转成 source ranges？ | `core.locateEvidence`（已存在，含 0/1/多命中的逐字裁决）→ 换算坐标 → 聚类（间距 ≤400）→ 扩展到段落边界 → 见 §3.1。全程零 AI 决策。 |
| 5 | 如何避免父级 scope 泄漏到子节点？ | 三重：① §3.1 第 ④ 步**交集钳制**（与父 span 无交集者直接丢弃并记 `scopeConflict`）；② 深挖输入**只从 `sourceSpans` 取**，不存在回退到 `unitAnchors` 的路径；③ 校验期断言 `child.sourceSpans ⊆ parent.sourceSpans`，违反即拒（有测试）。 |
| 6 | 单请求最多几层递归子树？ | **由 §6 的 A/B benchmark 决定，不预设**。工程上先把 1/2/3 层做成同一开关（`expandRecursionDepth`），引擎的 section/merge 装配路径**已支持嵌套递归**（`assembleTocLayer` / `attachMergeGlobal` 内的 `expand()` 递归），只有 expand 装配丢弃嵌套——补齐即可三档可切。 |
| 7 | 单请求最多输出多少节点 / token？ | `maxNodes` 按深度 8 / 25 / 60 + `MAX_OUTPUT_TOKENS` 初值 12,000（实测每次 completion 中位 ≈8 千，留 1.5 倍余量）；触发即 `OUTPUT_OVERFLOW`，**降级不截断**（§3.4）。 |
| 8 | 如何并行独立 scope？concurrency 怎么定？ | 任务单位 = (节点, span shard)；worker pool + 每 run 组级 AbortController；可并行面见 §3.6。concurrency 从 1 起，靠配置 + 自适应阶梯逐级放开，**默认保守**。 |
| 9 | 429 如何退避？timeout 如何处理？ | §3.6：`Retry-After` 优先 → 指数退避 + jitter → `concurrency = max(1, floor(c/2))` + 冷却窗口防震荡。§3.7：120 秒无数据 = `timeout`；8 分钟墙钟 = `timeout` 且必须与用户取消可区分；流已开始的失败 = `unknown_outcome`，不盲目重试。 |
| 10 | 目标 request / token / wall？ | §5 表（**全部标 provisional**，由 benchmark 替换）。 |
| 11 | 何时算 completed / partial？ | `completed` = 预算内无 `output_overflow`、无未补残余（`coverageGap` 为 0）、review 通过；否则 `partial`（存未激活版本 + 明确文案）。`section_ready` 永远不等于 completed。 |
| 12 | 关软件后如何恢复？ | 分片缓存 + 调用日志持久；启动对账把 `processing` 归为待续（§3.10），提示用户一键续跑，从缓存继续、不重复计费。 |
| 13 | 如何保证 preview 与实发一致？ | 同一 payload builder（现状契约保留）+ 阶段 A/B 双 preview（§3.9）+ 缓存键含 `spanHash` + 「planned vs attempts」口径分离。 |
| 14 | 如何证明详细度没下降？ | §7：`core.computeMapMetrics`（已存在：evidenceCoverage / branchingFactor / maxDepth / duplicateNodeRate / genericParentRate / tocEchoRate）+ 新增 coverageGap + `m15r-golden.json` 语义对照，修复前后同 fixture 对比。 |

## 5. 端到端模拟（**provisional，非验收标准**）

### 5.1 实测常数（来自审计，全部为本机真实运行）

| 常数 | 值 |
|---|---|
| 单次调用墙钟 `c_call` | 中位 **36 秒**（15–70 秒），与输入规模无关 |
| prompt/字符比 | **0.60** token/字符 |
| 单次 completion（含 reasoning） | ≈ **8,000** token（token_used 中位 1.3–1.5 万，减 prompt） |
| 首层分片数 | **17**（131,633 字符 ÷ 8,000，按段落边界） |
| 首层实测耗时 | 17 次 = **9 分 25 秒** |
| 每次调用产出子节点 | 6.45（中位 7） |
| 可展开比例（**坏作用域下测得，不可外推**） | 94.3% |

### 5.2 修复前的成本模型（实测对照）

```
每节点成本 = 1 作业 × 17 片 × 36 秒 ≈ 10 分钟
本书一级节点 ≈ 17 片 × 6.5 ≈ 110 个
完整深挖 ≈ 110 × 17 ≈ 1,870 次调用 ≈ 18.7 小时（预算 300 会在 3 小时处截断为 partial）
实测：上午会话 4 个作业用掉 64 次调用 / 50 分钟，队列仍有约 90 个一级节点未动
```

### 5.3 修复后的成本模型

```
首层           = 17 次（不变）
每个一级节点   = 1 次（span 中位 ≈2,000 字符 ≈1,200 token，单 shard；仅当 span >6,000 字符才拆片）
一级深挖       = ≈110 次
二级及以下     = 由「分支数 b × 继续可展开比例 f」递推：可展开节点数(next) = 可展开节点数(prev) × b × f
```

`b` 与 `f` 是**唯一未测参数**（坏作用域下测得的 94.3% 不可用），故给三种情形：

| 情形 | b | f | 一级 | 二级 | 三级 | 四级 | 合计调用 | 串行墙钟 | 并发 4 |
|---|---|---|---|---|---|---|---|---|---|
| 保守 | 6 | 0.50 | 110 | 330 | 990 | — | **预算触顶 300** | 3.0 h | 45 min |
| 中性 | 4 | 0.35 | 110 | 154 | 54 | 19 | **≈ 337** | 3.4 h | 50 min |
| 乐观 | 3 | 0.25 | 110 | 82 | 20 | 5 | **≈ 217** | 2.2 h | 33 min |

**结论一（必须写进产品预期）**：即使作用域修好，「完整深挖到原子层」在 13 万字材料上仍是**数百次调用**量级——所以 v48.11 的产品形态是**分层交付 + 预算可控**（首层约 10 分钟可见，深挖按预算推进、状态诚实），而不是「跑完为止」。

**结论二**：输入侧收益巨大，输出侧不变。

| 口径 | 修复前（实测） | 修复后（预算 150，provisional） |
|---|---|---|
| 调用总数 | 本书实测 113 次且未完成 | **150 次**（= 预算；17 首层 + 133 深挖） |
| 输入 token | 单轮 S3 已 187 万 | ≈ **28 万**（17×4,800 + 133×1,500） |
| 输出 token | 每次 ≈8 千 | ≈ **120 万**（150×8,000）——**新的主要成本与耗时来源** |
| 串行墙钟 | 67 分钟且未完成 | ≈ **90 分钟** |
| 并发 4 墙钟 | — | ≈ **23 分钟** |
| 最坏墙钟 | 无上界（预算只挡 expand） | 预算 ÷ 并发 × 36 秒 + 重试余量 → **≈ 30 分钟** |

### 5.4 口径对齐（避免以后对不上账）

```
17 section + 133 expand/gapfill + 15 merge/global/editorial/review = 165 计划调用
报告中出现的「总输出 ≈ N × 8,000」必须使用 165（不是 150）为基数；预算 150 只计 AI 结构生成类调用时需显式注明。
```

> 上表采用「预算 150 含尾部 15」口径，故写作 150；若按 165 口径，输入 ≈31 万、输出 ≈132 万、并发 4 ≈ 25 分钟。**两种口径都保留，实施时以运行总账为准。**

### 5.5 不可压缩部分

- 首层 17 × 36 秒 ≈ **10.2 分钟**是硬成本（同一材料、同一分片策略、同一模型下不可压缩；减小分片粒度只会增加调用次数）。
- 每次调用 ≈8 千输出 token 由 provider 的思考档决定；本应用当前**无法关闭**（`reasoning_effort` 只对特定模型族生效）。压缩输出属于 P2 议题，不在本方案范围。

### 5.6 对「一分钟级」的正式否定

Gemini Notebook 的 Mind Map 官方定义是「主要主题与相关概念的速览」；本项目目标是「作者组织结构的完整拆解」。**本方案不承诺分钟级**，只承诺：把无效重复推理消掉、把剩余请求做成可安全并行、并把进度与成本做成诚实可读。

## 6. A/B benchmark 协议（决定 §3.4 的递归深度默认值）

**控制变量（必须完全相同）**：材料 = 本书（约 13 万字）；`sourceSpans` = 同一份冻结快照；model / promptVersion / generatorVersion / modelConfig / temperature / `MAX_PAYLOAD_CHARS` / `maxNodes` / `MAX_OUTPUT_TOKENS` 全部固定。

**关键做法（冻结 fixture）**：先跑一次首层（结果入缓存），把首层产物（节点 + `sourceSpans`）**导出为 fixture 文件**；三档策略都从这份冻结件起跑——保证 spans 逐字节相同，唯一自变量是递归深度。

**自变量**：`expandRecursionDepth ∈ {1, 2, 3}`。

**重复**：provider 无 seed 保证 → **每档至少跑 2–3 次，取中位数并记录离散度**；一次跑分不得用于定默认值。

**指标（全表）**：

| 类 | 指标 |
|---|---|
| 成本 | calls、input tokens、output tokens、retries、cacheHits、actualCost |
| 时间 | wall time、TTFT、每次调用墙钟分布 |
| 结构 | validNodes、newNodes、evidenceValidNodes、maxDepth、branchingFactor |
| 覆盖 | evidenceCoverage、**coverageGapChars**、residual 比例分布 |
| 单位效率 | **costPerValidNode**、**wallTimePerValidNode** |
| 有效密度 | duplicateNodeRate、genericParentRate、tocEchoRate（复用 `core.computeMapMetrics`）——**节点多 ≠ 更详细** |
| 稳定性 | JSON failure、OUTPUT_OVERFLOW 次数、hardSplit 次数 |

**判定**：默认深度取「单位有效节点成本最低且覆盖不下降」的一档；不预设 2 层最好。

## 7. 质量不下降的证明方法

1. **同 fixture 前后对比**：`core.computeMapMetrics` 六项指标（已有实现）+ 新增 `coverageGapChars`；`evidenceCoverage` 与 `maxDepth` 不得下降。
2. **语义对照**：`tests/fixtures/m15r-golden.json`（教材/论证/技术文档三例的作者组织期望）保持人工比对基线。
3. **作用域完整性断言**（新）：`∀子节点：child.sourceSpans ⊆ parent.sourceSpans`；违反计数必须为 0。
4. **「原文错位」可检测化**：统计「节点 span 外仍有其证据引用」的记录数与 `scopeConflict` 次数，作为修复前后对照指标（当前实测表现为模型自报错位）。

## 9. 风险与回滚

| 风险 | 缓解 |

## 10. 测试计划（分层断言）

- **core**：坐标系与 `slice` 一致性（含 surrogate/emoji/combining）；span 推导六步逐条；聚类与扩展边界；`subtractRanges` 残余；覆盖度量口径（并集长度）；`locateEvidence` 多命中消歧回归。
- **engine**：深挖 payload **只含自身 span**（构造「父级 13 万字 / 子级 2 千字」夹具，断言 payload 上限与不含父级他处文本）；父级钳制（构造子级 evidence 落在父级之外的夹具 → `scopeConflict`）；gapfill 不重复请求（残余签名缓存命中）；输出溢出降级三级；预算统一（section/merge/global 都被挡）；429 退避与冷却；失败隔离；取消可区分「用户取消 vs 看门狗」；重启续跑。
- **db**：调用日志表与 run 总账字段；`spanHash` 入缓存键的唯一索引行为。
- **gui**：`partial` 文案（禁「生成失败」）；两阶段 preview 字段；后台增量不改变 transform；节点 id 稳定（选中态不丢）。
- **基准**：§6 的 fixture 冻结产物入库为测试夹具，供回归对比。
