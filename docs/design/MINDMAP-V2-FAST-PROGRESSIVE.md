## 0. 用户原话（2026-10-17，逐字留痕）

> 利用 AI 生成阅读材料的结构框架，让用户在开始学习前对材料结构有基本了解；并且结构框架的粒度可以按用户的需求继续向下扩展深挖，用户可以在生成的图谱末端点击进行扩展深挖。但如果检测到没有值得继续深挖的结构性内容，也就是如果结构触底了则要封顶。我所说的结构也要包含作者的论述结构、证明结构等等。在生成的过程中，已经生成的内容最好能先展示出来。
> 这种设计的依据是：有论文指出，"先掌握框架，再填充细节"的学习效率更高，且过程更轻松。
> 主要痛点是导图生成非常慢。……虽然我的导图粒度比它细得多，且支持扩展细节、深度挖掘，但也不能慢到这种程度。

**追加需求（2026-10-17，批准 Q1–Q8 时，逐字）**：

## 1. 一句话

> **慢的根因不是"粒度细"，而是"每个节点都要模型写一篇小作文、而且要等整篇写完才给看"。**
> v2 把模型的输出压缩到"每个节点一行"、把定位从"逐字引文"改成"段落编号"、把评审/润色移出关键路径、把调用并行化并流式解析——**粒度不降，首个节点出现时间从分钟级降到秒级，总输出 token 降到约 1/30–1/50**。

## 3. 现状诊断：为什么慢、哪里设计不合理

### 3.1 已被实测证实的事实

| 事实 | 来源 |
|---|---|
| 单次调用耗时**与输入长度无关**（8 千字与 13 万字都 ≈36s），**由输出 token（含推理）主导**：≈3s + 每 1,000 completion token ≈4.4s | v48.10 审计 §2；v48.12 §1.1 |
| 2,688 字文章：27 次调用、**92,434 completion token**、墙钟 **446s**，产出 72 节点 → **每个节点约 1,280 个输出 token** | v48.12 §1.1 |
| 默认并发 = 1，零重叠 | 同上；`concurrencyOf()` |
| 模型为 GLM 系推理模型，首字前约 40s 静默；GLM-5.3 思考无法关闭 | `docs/导图功能设计需求-给ChatGPT.md` §一；`ai.js` 注释 |
| 29% 的深挖调用零产出（模型说可展开，展开后什么都没有） | v48.12 §1.2 D1 |

### 3.2 根因（按影响从大到小）

1. **每个节点输出太"重"**。section 提示词要求每个节点输出 `title / authorialRole / centralQuestion / mainMove / progression / relationToParent / relationToSiblings / evidence[{unitAnchor, quote, startOffset}] / expandable / stopReason`——一个节点 150–300 个 JSON token，再加推理 token。**而用户在"先看框架"阶段只需要标题和类型**；其余字段是点开详情时才看的。
2. **逐字引文当定位手段**。为了可追溯，模型必须复制 5–30 字原文并给 offset；一字之差即整节点被拒、触发格式修复调用。它既贵（输出长）又脆（失败重试）。
3. **一次调用只出一层**（提示词明写「children 只给一层、不再嵌套」）。深度 D 需要 D 轮**串行**往返，每轮都要重新付一次首字等待。
4. **整篇写完才给看**。`chatOnce` 等全量文本 → `parseJsonLoose` → 校验 → 评审 → 落库 → 才广播。用户在第一个节点已经生成好的几十秒里看到的是空白。
5. **关键路径上挂了与"看框架"无关的阶段**：merge / global / editorial / review 串行跑在出图之前；review 闸门曾把 72 节点成品整张扣下（D45 事故）。
6. **推理模型做抽取**。结构抽取是"读懂并分段命名"，不需要长链推理；推理 token 是隐形的输出成本。
7. **工程复杂度反噬**：为补救上面几条，引擎累积了 shards / runs / calls 三账、Published/Candidate、interrupted 续跑、gap-fill、批量深挖 salvage、remap……`mindmapEngine.js` 3,133 行，每加一层补丁都让下一次改动更难。

### 3.3 NotebookLM 为什么快

它用的是 Gemini Flash 级**非推理**模型、**一次调用**、每个节点只输出**几个字的标签**、没有引文与评审；点击节点＝把节点名作为问题丢进聊天。**快 = 模型快 × 输出短 × 不等待**。
我们要的粒度更细、要可追溯、要论证结构——这些都可以保留，只要**不把它们全塞进首次生成的输出里**。

## 4. v2 设计原则（七条）

1. **输出最小化**：生成路径上每个节点**只输出一行**：层级号、类型、标题、原文段落区间、可否深挖。说明性文字一律**按需**生成（点详情时）。
2. **编号定位取代逐字引文**：本地先把原文切成带编号的块 `[12]`，模型只回 `@12-15`。区间由本地换算成 sourceSpans——**不可能引错原文**，只可能给出非法编号（本地直接丢弃该行）。
3. **流式逐行解析、边出边画**：每收到一个完整行就校验并推给画布；中途断流/触达输出上限 → 已收到的行全部保留，未完成的父节点标「＋」，**截断不再等于失败**。
4. **一次多层、自适应深度**：一次调用对自己的范围给出 2–4 层（按范围大小自适应），深挖一次给 1–2 层，减少串行往返。
5. **并行 + 优先级队列**：章节级任务并发（默认 4，遇 429 自动减半），用户点击 > 悬停预取 > 首轮章节（当前阅读章节优先）> 全书主线。
6. **质量闸门移出关键路径**：本地确定性校验逐行在线进行；AI 评审 / 润色改为用户显式触发的「精修此分支」，**不再阻断出图**。
7. **骨架零调用**：EPUB 导航、PDF 书签、Markdown/Word/HTML 标题、TXT 标题启发式 → 立即画出骨架；AI 只负责在骨架**之下**长出作者的组织结构。

## 5. 用户体验时间线（对比）

以 2,688 字基准文章（无目录）与 13 万字长书（有目录，约 20 章）为例；时间为**设计目标**，需在 P0 基准测量里验证（§12）。

```
现状（2,688 字）
0s ─────────── 31.6s 首层 section 完成 ── … ── 73s 首层可见（加 review）── 446s 全部深挖完
     （空白）                                      ↑ 用户第一次看到东西

v2（2,688 字，快模型）
0s 标题根节点 ── ~1–2s 第一个 AI 节点出现 ── 逐行长出 ── ~15–25s 三层框架完整
                                                     │
                                         点任一「＋」末端 → ~1–2s 出第一个子节点，≤10s 完成

v2（13 万字长书）
0s 目录骨架完整显示（0 调用）
~2s 当前阅读章节下开始长出结构；其余章节 4 路并行逐章填充
~1–2 分钟 全书各章前三层框架完整（20 章 ÷ 4 路 × 每章 15–20s）
```

画布状态语义（与 D46「没画出来 ≠ 没有更深内容」一致，强化为四态）：

| 节点外观 | 含义 |
|---|---|
| 实线 + 「＋」 | 有更深结构，尚未生成，点击即深挖 |
| 实线 + 折叠数「+N」 | 已有子节点，点击仅展开（零调用） |
| 实线 + 末端圆点「•」 | **已触底**（封顶），不会再出现深挖入口 |
| 虚线 + 呼吸点 | 正在生成中（流式进行中） |

## 6. 生成管线

### 6.1 本地预处理（零调用，打开图谱页签时后台进行）

1. **骨架**：复用现有 TOC → 提取单元树（`normalizeTocTree` 与「正文」伪节点修复保留）。无目录材料 → 根节点＝材料名。
2. **取文流水线化**：现状是渲染层把所有单元 `getSectionText` 全部取完才发主进程。v2 改为**逐单元取文、取到一章就排一章的任务**（当前阅读章节先取）。
3. **块切分 `segmentBlocks(linear)`（新，纯函数）**：
   - 以段落/块级元素为一块；>600 字的长段按句末标点再切；<20 字的碎块并入下一块（标题行除外）。
   - 块号在**整份材料内全局递增**，由 `sourceRevisionHash` 决定，同一文本切分恒等（入测试：100 次逐字节一致）。
   - 每块记 `[start, end)`（沿用 D44 的 UTF-16 一维坐标），因此「块区间 → sourceSpans」是确定性换算。
4. **作用域单元（job scope）划分**：
   - 有目录：每个叶章节一个 scope；>2 万字的章节按块边界切成若干 ≤1.2 万字的子 scope（在骨架上表现为该章的连续几段，模型输出仍挂到该章下）。
   - 无目录且 ≤1.5 万字：整份材料一个 scope。
   - 无目录且更长：按块边界切成 ≤1.2 万字的 scope，再加一个「全书主线」任务（§6.4）把它们分组命名。

### 6.2 首轮框架任务 `outline`（每个 scope 一次调用，并行）

- 输入：材料名 + 结构路径（骨架祖先标题）+ 本 scope 的**带块号原文**。
- 输出：本 scope 之下 **L 层**结构，L 按 scope 字数自适应：≤3 千字 → 4 层；3 千–1.2 万字 → 3 层；更大 → 2 层。
- 输出上限：`max_tokens ≈ 3,000`（约 100 行）；达到上限即停，已收到的行全部有效。

### 6.3 深挖任务 `expand`（用户点击「＋」或悬停预取）

- 输入：材料名 + 祖先路径标题 + **兄弟节点标题**（防止重复切分）+ 该节点**自身块区间**的带号原文（沿用 D44 作用域红线：不读父级原文）。
- 输出：该节点之下 1–2 层（区间 ≤8 块时 1 层即可）；`max_tokens ≈ 1,500`。
- 同一节点任何时刻只有一个 expand 在跑；结果按 `(docRevision, blockRange, promptVersion, model)` 缓存，重复点击/重生成零调用。

### 6.4 全书主线任务 `spine`（低优先级，可选）

- 仅在「无目录长材料」或「目录过平（一级 >12 项）」时自动排队；其余情况只在用户点根节点「＋」时触发。
- 输入：各 scope 已生成的**前两层行**（不发原文，几百到几千 token）。输出：几行「部分」分组（例：`P1 [问题] 优绩主义的承诺 @s1-s3`），把章节归入作者的宏观组织（问题→诊断→出路……）。
- 这是旧 global merge 的瘦身版：**几十到几百个输出 token**，且不阻断任何显示。

### 6.5 节点详情按需生成 `explain`（点详情时，可缓存）

- 用户选中节点 → 详情面板先立即显示：标题、类型、原文段落（就是块区间原文，天然逐字）、跳正文、就此制卡。
- 「这一部分作者在做什么？」按钮（或设置为选中即自动）→ 流式生成 2–4 句：核心问题 / 作者动作 / 与父、兄弟的关系。即旧版 `centralQuestion / mainMove / progression / relationTo*` 的**按需版本**，结果写回节点并缓存。
- 结构制卡（D43 card-structure）的语义包需要这些字段时，先触发一次 explain（若无缓存）。

### 6.6 退役的阶段

| 旧阶段 | v2 处理 |
|---|---|
| section（一层 + 重字段） | → `outline`（多层 + 单行） |
| expand（一层 + 重字段 + 逐字引文） | → `expand`（1–2 层 + 单行 + 块号） |
| merge（逐级归并） | **取消**：骨架提供上层结构；作者组织在章内由 outline 直接给出 |
| global | → `spine`（可选、轻量、不阻断） |
| editorial 终编辑 | **取消默认**；并入「精修此分支」 |
| review 语义评审（闸门） | **取消闸门**；并入「精修此分支」，结果只作建议 |
| gap-fill 覆盖补漏 | → 本地确定性：子区间未覆盖父区间的块显示为灰色「其余 N 段」可深挖桩（零调用） |
| STRUCTURE_FORMAT_REPAIR | **取消**：行协议下坏行只丢该行，不存在"整份 JSON 不合法" |
| Published / Candidate / interrupted 续跑 | 简化：任务粒度只有十几秒，中断＝重排队即可（§9.3） |

### 6.7 「精修此分支」（显式、可选）

节点菜单里的高级操作：用用户指定的「精修模型」（可设为强推理模型）对**一个分支**做一次合并重排：去重、修笼统标题、补遗漏的论证关系。输入＝该分支的行 + 区间原文，输出＝同一行协议的整枝替换。替换前后可对比、可撤销。**永远不自动发生。**

## 7. 封顶（触底）规则

三道门，任何一道判定触底即封顶（画末端圆点，不再给「＋」）：

1. **本地确定性下限（零调用）**——满足任一即不可深挖：
   - 区间 = 1 块且 < 300 字；或区间总长 < 120 字；
   - 深度 ≥ 8；
   - 区间内容是单一引文/单一公式块/单一图注（块类型判定）。
2. **模型标记**：每行末尾 `+`（内部仍有 ≥2 个可区分的结构部分：多个理由/步骤/情形/子论点/例子组）或 `.`（单一连续论述、单个例子、单个定义、纯过渡）。提示词明确：**判断标准是结构的独立组织意义，不是字数**（沿用 v48.5 口径）。
3. **深挖后回判**：expand 返回 <2 个子节点、或子节点覆盖的是同一块 → 该节点改记为触底并缓存（解决 v48.12 测得的 29% 零产出问题——同一节点不会被第二次白付费）。

逃生口：详情面板底部小字「仍要尝试深挖」（模型偶尔误判 `.` 时用户可强制），不在画布上显示。

## 8. 结构类型：把论述结构、证明结构纳进来

### 8.1 类型表（封闭枚举，中文短标签，输出成本 1–2 token）

| 族 | 类型 | 典型父子关系 |
|---|---|---|
| **论证** | 论点、理由、证据、例证、反方观点、反驳、让步、结论 | 论点 → 理由 → 证据/例证；反方观点 ↔ 反驳 |
| **证明** | 命题、前提、定义、引理、推导、分情形、结论 | 命题 → 前提/引理 → 推导步骤 → 结论；分情形 → 情形 1…n |
| **说明** | 引言、背景、问题、方案、分类、对比、因果、步骤、总结 | 问题 → 原因 → 方案；分类 → 各类 |
| **叙事** | 叙事、案例 | 案例 → 情节/要点 |
| 兜底 | 其他 | — |

旧 `authorialRole`（17 值）→ v2 类型有确定映射表（供旧图读取与 card-structure 兼容），实施时写进 `mindmapCore`。

### 8.2 关系边（论证/证明的非树结构；rev.2 扩为八类）

论证和证明不总是树：反驳指向某个反方观点，推导步骤会"用到"某条引理，后文的结论会回答前文的问题。行尾可附 0–3 个关系，语法 `&码目标`，语义统一为「**本节点 —码→ 目标**」：

| 码 | 关系 | 读法 | 画法（§15.6） |
|---|---|---|---|
| 支 | 支持 | 本节点支持目标 | 实线 + 实心箭头 |
| 驳 | 反驳 / 质疑 | 本节点反驳目标 | 实线 + 双竖杠端（⊣） |
| 据 | 依据 / 用到 | 本节点用到目标（前提、引理、定义） | 虚线 + 开口箭头，**画成目标 → 本节点**（前提流向结论） |
| 推 | 推出 | 本节点推出目标 | 粗实线 + 实心箭头 |
| 因 | 导致 | 本节点导致目标 | 中粗实线 + 实心箭头 |
| 比 | 对比 | 本节点与目标对照 | 细实线 + 两端圆点 + 「vs」 |
| 例 | 例示 | 本节点是目标的例子 | 点线 + 开口箭头 |
| 答 | 回答 | 本节点回答目标提出的问题 | 点划线 + 实心箭头 |

- **隐含关系不必输出**：子节点类型已蕴含它与父节点的关系（理由/证据/例证 → 支父；反方观点 → 驳父；引理/定义 → 被父据），由版式直接画出，零 token。
- **目标可引用**：同一次输出里已出现的层级号（`2.3`），或输入上下文里给出的全局短号（`#k7`）。outline / expand 的输入都附一份「可引用节点清单」（§15.5），使跨章节关系也能在**读到原文的那一次调用里**被标出——关系始终有原文依据（来源节点的块区间），不靠无原文的二次推断。
- 非法引用（目标不存在 / 自指）丢弃该关系、保留节点；每节点最多 3 条，超出截断计入账本。

## 9. 输出协议与流式解析

### 9.1 行协议（模型输出）

```
1 [问题] 优绩主义为何伤害所有人 @1-6 +
1.1 [背景] 招生丑闻引出的追问 @1-3 .
1.2 [论点] 赢家与输家同受其害 @4-6 +
2 [论点] 输家：被羞辱的"不配" @7-19 + {论证}
2.1 [理由] 失败被归为个人责任 @7-11 +
2.2 [证据] 民调与死亡率数据 @12-15 .
2.3 [反方观点] "机会平等就够了" @16-17 .
2.4 [反驳] 平等起点也会固化等级 @18-19 . &驳2.3
```

- 每行：`层级号 [类型] 标题 [〈时间〉] @起块-止块 (+|.) [{版式}] [&码目标 …]`；标题 ≤20 字，可抽象命名但须忠于该区间原文。
- `〈时间〉`（可选，紧跟标题）：叙事/历史类节点的时间元信息（`〈约前 470〉` `〈1872〉`），供时间线版式使用；只能来自原文。
- `{版式}`（可选，仅对**将有子节点**的行有意义）：`{树}` `{链}` `{时间线}` `{分层}` `{论证}` `{对照}` `{网格}`——模型对"这一组子结构该怎么排"的提示（§15.4 第②级），1–2 token；因为父行先于子行输出，渲染层在第一个子节点到达前就知道该用什么版式，避免流式途中改版式造成跳动。
- 每行约 20–30 token（旧 JSON 节点 150–300 token，另加推理）。
- 层级号是路径式（`2.1` 的父是 `2`），所以**任意前缀都是一棵合法的树**——这正是能边出边画的前提。

### 9.2 本地逐行校验（替代旧 §4.19-6 的整树校验，规则不放松，只是变成在线）

| 检查 | 不通过时 |
|---|---|
| 行格式可解析 | 丢弃该行（累计计数入账本） |
| 父层级号已存在 | 丢弃（并丢弃其后代） |
| 块区间合法、且落在父区间内 | 钳制到父区间；无交集则丢弃（沿用 D44 `scope_conflict` 语义） |
| 类型 ∈ 枚举 | 记为「其他」 |
| 同父下标题重复 / 区间完全相同 | 后者丢弃 |
| 笼统空盒标题（「概述/内容/相关知识」…） | 保留但加警告标（不阻断） |

覆盖账：一个 scope 完成后，本地计算父区间里未被任何子区间覆盖的块；≥2 块的缺口生成灰色「其余 N 段」桩节点（可深挖），**零调用**，取代 gap-fill。

### 9.3 传输与持久化

- `ai.js` 新增 `chatStreamLines({ onLine })`：在既有 SSE 解析上做行缓冲，**不改动其余调用方**。思考模型的 `reasoning_content` 不进入解析器。
- 主进程每解析出一批行（≤100ms 节流）广播 `mindmap:delta { documentId, mapId, jobId, nodes[] }`；渲染层增量合入。
- **落库粒度＝任务**：任务完成（或被中断）时把已校验行**事务性**写入 `material_map_nodes`（新表，见 §10.1）→ 符合不变量 4（better-sqlite3 下单事务写入代价很小，无需登记例外）。
- 应用关闭/崩溃：只丢失"正在流式的那个任务"的未落库行；重启时该节点仍显示「＋」，重排队即可。**不再需要 interrupted 状态机**。
- 传输层既有能力全部保留：finish_reason（`length` 时未完成父节点标「＋」而不是失败）、usage、abort 归因、429/5xx 重试与「流已开始不重试」纪律。

## 10. 数据模型与调度

### 10.1 存储

| 表 | v2 |
|---|---|

| `material_map_nodes`（**新**） | 每节点一行：`mapId, nodeId(全局短号), pathNo, parentId, ord, title, type, patternHint, blockStart, blockEnd, spansJson, state(open/more/floor/stub), source(toc/ai/local), explainJson, jobId, createdAt`——增量写入不必重写整份 JSON |

| `material_maps.viewJson`（**新列**，rev.2） | 视图偏好：每组手动版式、折叠集合、（P6）手动微调偏移。**只是视图，不是结构**——删掉它图照样能完整重建 |
| `material_map_calls` | 保留为**唯一账本**（每次调用一行：kind=outline/expand/spine/explain/refine、token、耗时、TTFT、行数、丢弃行数） |
| `material_map_shards` | 改作输出缓存（键见 §6.3） |
| `material_map_runs` | 降级为"一次用户动作"的分组记录（生成整图 / 深挖全部），不再承载状态机 |

旧 v1 图（`structureJson` 内嵌节点）：读取时经适配器转为 v2 节点（`sourceSpans → 块区间`、`authorialRole → 类型`），**只读显示**、可继续在其末端深挖（深挖产物写 v2 节点表）。

### 10.2 调度器（主进程单例）

- 优先级：P0 用户点击深挖 / explain → P1 悬停预取 → P2 首轮 outline（当前阅读章节、可视区章节优先）→ P3 spine / 深挖全部。
- 并发：默认 4（设置 `app.mindmapConcurrency` 已存在，默认值 1→4）；429 → 降半 + 60s 冷却，连续 3 次成功升档（沿用 D44 阶梯）。
- 同一材料同一节点串行化（沿用 D48 守卫，但粒度从"整份材料"细化到"节点"——这样深挖 A 分支时可同时深挖 B 分支）。
- 任务生命周期仍由主进程持有，离开页签不取消（沿用 §4.19 收口⑤）。

### 10.3 悬停预取（默认开，可关）

鼠标停在「＋」节点上 ≥400ms（或键盘焦点停留）→ 以 P1 预先发起该节点 expand；用户随后点击时结果已经在流或已完成。每份材料每天预取上限默认 30 次，计入账本，可在设置关闭。
**理由**：这是 NotebookLM 那种"点开即有"体感的来源，成本只花在用户确实在看的节点上。

### 10.4 模型分层（新设置，默认跟随全局 AI 服务）

- `app.mindmapModel`：框架/深挖用的模型。设置页明确推荐**非推理快模型**（如 GLM-4.7-Flash、DeepSeek-Chat、Gemini Flash、Qwen-Plus），并附「测速」按钮（测 TTFT 与 token/s，结果显示在下拉旁）。
- `app.mindmapRefineModel`：精修此分支用的模型，默认跟随全局（可选强推理模型）。
- 若用户坚持用无法关思考的推理模型：功能照常，但界面在生成区如实提示"当前模型带思考过程，首个节点约需 N 秒"（N 取测速值），**不伪装进度**。

### 10.5 成本与速度估算（设计目标，待 P0 实测校准）

| 指标（2,688 字基准） | 现状实测 | v2 预计 |
|---|---|---|
| 调用次数（框架到 3–4 层） | 27 | **1** |
| completion token | 92,434 | **≈1,500–2,500**（≈60–80 行） |
| 首个节点出现 | 73s（首层整块出现） | **TTFT + ≈1s**（快模型 TTFT 通常 <2s） |
| 框架完整 | 446s | **≈15–30s** |
| 单次深挖 | 14–36s，29% 零产出 | **≈3–10s**，触底节点零调用 |

13 万字长书：现状首层 17 次串行 ≈10 分钟、深挖到底不可行；v2 目录骨架 0s、首章结构 ~2s 起流、全书前三层 ≈20 次并行调用 ≈1–2 分钟，输入 token ≈1× 全书（每块原文首轮只发送一次）。

## 15. 视觉层：从「树」到「结构画布」（rev.2 新增）

### 15.1 数据模型：复合图

图 = **包含层级**（containment，谁属于谁）+ **关系边**（relation，谁和谁有什么关系）+ **每组版式**（view，这一组怎么排）。

- **为什么不干脆改成一般图**：深挖、封顶、覆盖账、区间钳制、"其余 N 段"桩全都依赖包含层级——"这一段原文由谁负责"必须唯一。论证与证明的"图性"主要发生在**同组或近邻**之间，用关系边叠加在层级之上即可完整表达，而不必牺牲层级带来的可深挖性。
- 包含层级 = 原文区间的嵌套（父区间 ⊇ 子区间）；关系边可任意跨层、跨章。
- 版式是**视图**，不改结构：同一张图换版式不调用 AI、不改库里的节点与边。

### 15.2 关系边

八类关系的定义与语法见 §8.2。视觉语法只有一条总纲：**直角线是结构，曲线是关系**。

- 结构线（父子包含、链/时间线的先后）：1px 直角折线 / 直线，`--border-strong` 灰。
- 关系线：曲线，`--text-secondary` 色，按 §8.2 表区分线型与端头；**不用颜色区分关系类型**（守单 accent 原则，也照顾色觉差异）；只有与选中/悬停节点相连的关系变 accent。
- 关系标签（「依据」「反驳」…，11px）只在高亮时或缩放 ≥0.8 时显示；「对比」常显 `vs`。

### 15.3 版式库（七种）

| 版式 | 适用（典型信号） | 几何 | 组内边 |
|---|---|---|---|
| **大纲树** | 默认；说明、分类不多的层级 | 父卡在左，子块纵向排在右侧（现有 tidy tree 推广到"子块为任意矩形"） | 直角结构线 |
| **链** | 步骤、推导、递进、问题→原因→方案 | 子块纵向串联（流程类可横向） | 相邻先后箭头 |
| **时间线** | 叙事、历史、阶段；子节点带时间元信息 | 水平时间轴 + 刻度 + 时间标签，子块沿轴排列 | 时间轴本身 |
| **分层图** | 证明（定义/引理/前提 → 推导 → 结论）、因果网 | 按"依据/推出/导致"做最长路分层，自上而下；层内重心法排序（让下层对齐前驱，跨层边自然走两侧通道） | 组内关系曲线，常显 |
| **论证图** | 论点 + 理由/证据/例证/反方/反驳 | 论点居中在上；支持方一侧、反方一侧；反驳挂在它针对的反方观点下方；理由下的证据**同版式嵌套并入同一框**（不再套框） | 向上指向论点的支持/反驳线（隐含关系，零 token） |
| **对照** | 对比、两类/多类事物的属性对应 | 每个对比项一栏，栏内属性逐行对齐（同一行＝同一维度），栏间 `vs` | 栏间对比线 |
| **网格** | 分类/枚举 ≥6 项且项间无关系 | 自动列数（⌈√n⌉）等宽格 | 无 |

除大纲树外，其余版式都以**轻框**呈现：1px hairline 矩形，父节点卡片作框头，右上角 11px 小字标注「版式 · 来源」（如「论证图 · 模型提示」），框本身可点选、可折叠。

### 15.4 自动选择（两级、确定性、本地）

**组级**（每个有可见子节点的父节点），优先级从高到低：

1. **手动**：用户在节点详情里选的「排列方式」（存 `viewJson`）。
2. **模型提示**：父行的 `{版式}`（§9.1），本地校验其前提成立（例：`{对照}` 至少 2 个子节点）才采用。
3. **本地规则**（按序取第一个命中）：

| # | 条件 | 版式 |
|---|---|---|
| 1 | 子节点全部带时间元信息，或 ≥75% 为「叙事」 | 时间线 |
| 2 | 父为「论点」，或子节点含「反方观点」，或「理由/证据」≥50% | 论证图 |
| 3 | 父为「对比」，或子节点间存在「比」关系，且子节点 ≥2 | 对照 |
| 4 | 子节点 ≥3，且子节点之间「据/推/因」边数 ≥ 子节点数−1 | 分层图 |
| 5 | 「步骤/推导/前提/结论」≥60% | 链 |
| 6 | 子节点 ≥6、都没有子节点、彼此无关系 | 网格 |
| 7 | 其余 | 大纲树 |

4. **超量保护**：可见子节点 >12 时任何版式都启用 LOD（显示前 7 项 +「另有 N 项」），沿用 7/12/24 语义缩放。

**材料级**：按全图节点类型族占比给出整体图式标签——论证型 / 证明型 / 说明型 / 叙事型 / 混合型——显示在画布左上角（「本图按『论证型』组织」）。它只影响根组的默认版式与方向偏好，**不覆盖组级选择**；所以混合材料（教材里一章含一段证明、一场争论）天然各得其所。

### 15.5 生成侧配合（成本极小）

- 父行 `{版式}` 提示：每个父节点 +1–2 token。
- 关系 `&码目标`：只标非隐含关系；按基准估算全图 +5%–10% 输出 token。
- 「可引用节点清单」随输入发送：outline 附目录骨架的章节短号与标题、已完成章节的前两层（短号 + 标题）；expand 附祖先、兄弟、与目标已有关系的节点、本章前两层。清单只有标题，不含原文，每次几百 token 输入（输入不是耗时主因，§3.1）。
- 提示词里给论证 / 证明 / 对照三段 few-shot（P0 校准）。

### 15.6 组合布局与关系路由

**组合布局（嵌套块）**：每组自底向上算成一个块（宽、高、子元素相对坐标、锚点＝该组父卡片），父组只把子块当作矩形摆放。因此：

- 任何一组内部的变化只影响**它自己和祖先链**的重排，其余子树作为整体**刚性平移**（§15.8 S2 的实现基础）。
- 每组布局结果按「组 id + 子块尺寸序列 + 版式 + 视图偏好」缓存，增量更新只重算脏链，O(深度 × 组大小)。
- 坐标全部取 4px 网格整数；纯函数、无随机源（沿用 D42 确定性红线）。

**关系路由**：

- **组内关系**由版式本身排布（分层图的层间曲线、论证图的向上支持线、对照的栏间 vs），恒显示。
- **跨组关系**：曲线；若直连会穿过卡片或**不包含任一端点的组框**，则改走**通道**——绕到障碍物外侧的空隙里纵向（或横向）通过，再弯入目标。障碍判定按路径长度密采样；同一通道内的平行边按 4px 分道。
- **端点挂框**：端点已展开成组框时，关系挂在**框边**而非框头卡片（"反驳的是这一整段论证"）；同组内父子之间仍连卡片。
- **端点提升**：端点被折叠或尚未生成时，挂到最近的可见祖先；同一对可见端点间的多条同向关系合并为一条并标「×N」。
- **防毛线团的显示策略**：跨组关系默认不画线，只在卡片右上角显示「↗N」计数；悬停或选中节点时画出它的全部关系；工具条「全部关系」开关一次画全（淡色）。

### 15.7 关系透视（focus）

选中节点后开「关系透视」：与它无关的卡片与框降到 35% 不透明度，它的关系线、关系对端与祖先链保持全亮；节点详情面板同步列出关系文字清单（「依据 → 欧多克索斯建立比例论」「← 反驳：…」），点击即飞到对端。文字清单同时是**无障碍与键盘通路**：Tab 进入清单、Enter 跳转，不必在画布上追线。

### 15.8 自然扩展：稳定性契约 S1–S8（实现必须满足，均可机械测试）

| # | 规则 | 测试 |
|---|---|---|
| S1 | **顺序不变**：同组子节点按原文顺序（块起点）排列；已有节点永不重排 | 新增节点后，旧节点在组内的次序不变 |
| S2 | **块外刚性平移**：一次变化只重排"变化组 + 祖先链"；链外任何子树内部相对坐标逐字节不变 | 布局前后对链外子树做相对坐标比对 |
| S3 | **锚点不动**：用户操作的节点（点了「＋」、切了版式、折叠了）在屏幕上的位置不变（视口反向补偿）；流式生成整图时以根或当前聚焦节点为锚 | GUI：锚点屏幕位移 ≤1px |
| S4 | **单调生长**：一个任务流式进行期间，该组框只增不减；布局更新节流 ≤4 次/秒 | GUI：采样框高序列单调不减 |
| S5 | **版式迟定一次**：任务开始时按模型提示定版式；任务结束时规则复核，最多再变一次（带形变动画），之后锁定，除非用户手动改 | 单测：一个任务内版式变更次数 ≤1 |
| S6 | **叶就地长成框**：叶子被深挖为非树版式时，原卡片原地成为框头（左上角不动），框体向下/向右长出 | GUI：深挖前后框头卡片坐标不变 |
| S7 | **生长方向一致**：大纲树向右长，框向下长；兄弟只被向下（或向右）推开，不会被挤到上方 | 单测：受影响兄弟的 Δy ≥ 0、Δx ≥ 0 |
| S8 | **动效节制**：新节点从父卡片位置淡入 + 位移 240ms，旧节点位移过渡 260ms（ease-out），离场淡出；`prefers-reduced-motion` 下全部瞬时 | GUI：reduced-motion 下零过渡帧 |

缩放层级（LOD）：整体缩小到 <0.5 时，深层框收成摘要卡（「论证图 · 6 个子结构」），只留标题；放大即还原——缩放本身不触发重排，只切换渲染粒度。

### 15.9 画布交互（在现有基础上增量）

保留：滚轮缩放、拖动平移、适应窗口、搜索定位、导出自包含 SVG、键盘可达。
新增：组框点选/折叠；节点详情「排列方式」切换（自动 / 七版式）；「全部关系」「关系透视」开关；关系计数 ↗N；小地图（节点 >300 时出现）。
延后（P6）：拖动微调位置（pin，存 `viewJson`，自动布局视 pin 为组内固定偏移）——自由画布手感有价值，但会与 S2 冲突，需先有稳定的自动布局再加。

### 15.10 为什么自研布局而不引入 ELK / dagre

| 方案 | 结论 |
|---|---|
| ELK（elkjs，EPL-2.0，约 1.5MB） | 复合图分层布局与正交路由很强，但它是**整体重排**：局部深挖会让无关分支一起移动，直接违背 S2/S3；需 Worker 异步；且 D42 已定"自研纯函数确定性布局" |
| dagre（MIT） | 只有分层图，复合节点支持弱，同样整体重排 |
| **自研「块组合 + 七版式 + 通道路由」** | 采纳：天然满足刚性平移与确定性；每个版式几十到一两百行；分层图的组规模小（≤24），简单重心法足够；路由只服务跨组边且有显示策略兜底 |

样张 `design-samples/mindmap-v2-canvas.html` 即按此方案实现的最小原型（约 580 行，含七版式、端点挂框、通道绕行、锚点补偿、流式演示），作为 T18–T21 的参考实现与视觉验收基线。
