## 2. 事实基础（研究结论，2026-10-04 核实）

### 2.1 ASD-STE100 是什么

- 现行版本 **Issue 9，2025 年 1 月**发布，副标题升级为 "Standard for Technical Documentation"；由 ASD 下设 STEMG 工作组维护，约每 3 年一版，官方站可免费下载 PDF。
- 两大板块：**写作规则**（53 条，按"程序性写作/描述性写作"两类文本组织）+ **受控词典**（约 900 个批准词，"一词·一词性·一义"原则）。
- 有代表性的量化约束：指示句 ≤ 20 词、描述句 ≤ 25 词；一句一个指令；一段一个主题（≤ 6 句）；名词短语 ≤ 3 词；动词只允许限定形态（主动语态优先，施动者不明才可被动）。
- 性质：它是**写给技术文档作者的控制性写作规范**，不是"解释文本用的教学法"。我们的功能是借它的规则框架去**检测**文本的歧义/复杂点，并按其精神**改写**——这是对 STE 的创造性使用，不是合规检查器。

### 2.2 法务边界（决定架构的一票）

- 官方声明：Simplified Technical English、ASD-STE100 是 **ASD（布鲁塞尔）的版权与商标**（EUTM 017966390），All rights reserved；免费下载 ≠ 允许再分发或内嵌。
- ASD 相关材料明确：**若要将 ASD-STE100 改编为其他语言，必须向 ASD 申请许可**，按与原规范同等的条件授予。
- 推论：
  1. "中文版/日文版 STE 规则文本"不能由我们翻译制作并内置分发；
  2. STE 的批准词典词表不能复制进 prompt 或资源文件；
  3. 可以做的：引用名称与版本号（事实性引用）、以**自写文字**蒸馏其规则精神、让模型凭借其自身对 STE 的既有知识执行任务（prompt 只下指令与给约束，不粘贴规范原文）。
  4. 本项目当前无用户侧模板编辑 IPC（只有 `prompts:list/get`，见 `electron\main.js:646-647`），不存在用户粘贴规范原文的内置通道；将来若开模板编辑，需在 UI 加"请勿粘贴受版权保护的规范全文"提示。

### 2.3 多语言世界的既有坐标

| 语言 | 可挂靠的公开标准 | 性质 |
| --- | --- | --- |
| （语言中立） | **ISO 24495-1:2023 Plain Language — Part 1** | 首个国际简明语言标准，**明确语言中立**，四原则：读者能找到、能理解、能使用（+相关）。是我们 universal 兜底 pack 与全部分类的原则锚。 |
| 日语 | **やさしい日本語** | 有日本官方手册（法務省出入国在留管理庁《「やさしい日本語」の手引き》、总务省消防庁指南）；公认"8 条基本规则"（先说结论、短句、明确施受关系、避免敬语/难汉字/片假名术语等）。 |

## 3. 概念重构：从"X 语版 STE"到"受控语言剖面 CLP"

用户原始设想是"界面中文→用中文版 STE"。经 §2.2/§2.3 核实，这条路在法务与事实上都不成立，等价的正确构造是：

**CLP（Controlled Language Profile）= 公共规则分类法（语言中立）+ 每语言实例化参数（人工撰写）**

- **公共分类法**（自写蒸馏，结构参照 STE 的规则门类，原则锚定 ISO 24495-1）分五组：
  1. 词汇（一词一义；术语首现即定义；避免多义/比喻/行话）
  2. 句法（短句上限按语言；一句一义；限定从句嵌套深度；显式施受关系）
  3. 语态（主动优先；施动者不明须声明"来源未说明"）
  4. 篇章（一段一主题；先结论后展开；指代显式化）
  5. 数量与条件（数字/单位/量级明确；隐含前提显式化）
- **每语言实例化**：句长上限在中文/日文不能沿用"20 词"（词不对应），由 pack 以该语言可执行的近似约束给出（如 zh ≤ 40 字/句、ja "一文一義・従属節は1つまで"），并引用该语言已有公开标准作为依据（§2.3 表）。
- **模型执行**：LLM 对 STE 本身有充分的内在知识；prompt 只需 (a) 下达任务（§4），(b) 注入目标语言的 pack 约束（原生语言书写，禁止运行时机器翻译规则），(c) 给出输出契约。不需要也不允许把规范原文塞进 prompt。

这样"多语言适配"从"翻译一份规范"（不可能）变成"注册一个 pack"（可增量、可回退、可测试）。

## 4. 功能设计：任务定义与输出契约

### 4.1 任务定义（总是完整执行，AI 不做"是否值得解读"的门控）

用户在解读方式切换器中选择"简明解读"，即表示**由用户自己判定这段材料需要简化处理**——AI 不再自行判定"已足够清晰"并提前短答。流程恒定为：

1. **歧义点清单（可为空）**：每个点 = 原文片段引用 + 类别标签（封闭集，见 4.3）+ 两三句说明（为什么在此上下文易歧义）。若没有任何类别命中：正文**省略歧义点节**（不写"本段无歧义"之类的空节），机器标记 `<!--ste:points=0-->` 照常输出（供 UI 轻提示/统计用），直接进入下一步。
2. **受控改写（总是执行）**：按输出语言的 CLP 逐句改写。输出语言 ≠ 材料语言时，改写同时是翻译（如中文界面读英文书）。改写与原文保持句级对应（便于对照）。文本清晰但句子长/结构重时，这一步就是价值所在——这正是"门控取消"后仍要完整执行的理由。
3. **多重解读并列（如适用）**：当歧义允许 ≥2 种读法，各给一行释义 + 结合上下文哪个更可能。另附小型术语表（≤5 条，如适用）。

### 4.2 输出契约（流式 Markdown + 机器注释标记）

沿用现有流式 Markdown 渲染（`AIPanel.tsx:131-137`），不新增渲染组件（P0）：

- **机器标记**：正文前部输出 HTML 注释（Markdown 渲染不可见、正则可解析，为 P2 结构化升级预留，P0 仅用于测试断言与轻提示）：
  ```
  <!--ste:matLang=en-->
  <!--ste:points=3-->
  <!--ste:readings=2-->   (可省；points=0 时本标记与歧义点节一并省略)
  ```
- **正文章节**（节标题用输出语言书写，顺序固定）：歧义点（每点一行：`类别 · 原文片段 → 说明`；points=0 时整节省略）→ 简明改写 → 多重解读（如有）→ 术语（如适用）。

### 4.3 歧义类别封闭集（语言中立的 key，展示名按 locale 渲染）

`polysemy`（一词多义）· `pronoun-ref`（指代不明）· `long-nesting`（长句/嵌套）· `hidden-agent`（施动者隐藏）· `negation-stack`（否定叠加）· `undefined-term`（术语未定义）· `register-mix`（语域混杂，如文白夹杂）· `quantity-vague`（数量/量级含糊）· `idiom-figurative`（比喻/成语）· `missing-condition`（隐含前提）

封闭集存于渲染层常量，prompt 中枚举 key；模型只能从中选。新增类别 = 契约变更（bump 版本 + 决策号）。

### 4.4 命名（已拍板）

| locale | 主名 | 辅助说明 |
| --- | --- | --- |
| zh-Hans | **简明解读**（定稿） | 副标：受控语言 · STE 思路 |
| en | Plain decode | STE-inspired controlled language |

### 5.2 方案 A 细节

### 5.3 点击行为契约（v5 定稿）

回应质询"是否应在右侧边栏展示可选项、用户确认后再开始"。先澄清事实边界，再定契约：

**事实边界（本设计零改动）**：
- "AI 解释"与"AI 制卡"是两个独立按钮、两条独立流程（`aiPanel.kind: "explain" | "cards"`），点"AI 解释"永远不会触发制卡。
- 卡片入队永远经显式"接受"闸门（`AIPanel.tsx:398-411`，记忆接地存疑另有二次确认）；解释面板"就此制卡"也是显式按钮（`AIPanel.tsx:145-148`）。不变量 2（AI 不是事实源）不受切换器影响。

**契约**：
1. **方式状态三态**：`explainMode: "auto" | "general" | "ste"`，默认 **auto（自动）**。显式选择（general/ste）会话内记忆；切回 auto 即恢复自动。
2. **点击即执行（无条件，v5）**：点击"AI 解释"立即发起请求。方式解析顺序：**显式选择 > auto=本地路由器**（§5.4，纯前端、零成本零延迟）。**不设"解释前确认方式"开关**——v5 用户裁定删除：三态切换器（显式选通用/简明）+ 自动路由已覆盖原开关的全部场景，不为低频路径增加一个设置项。
3. **切换即重跑**：流式进行中切换器可操作；切换 = 清空答案、按新方式重发（沿用 `runExplain` 既有语义，`useSelectionActions.ts:811-836`）。`src/lib/ai.ts:59-98` 的 requestId 配对已保证旧流不串扰新结果（正确性无需新增机制）。
4. **一致性依据**：与制卡分支"点击即生成 + 事后按类型重跑"（`actAICards` 点击直达 `runAICards`；`AIPanel.tsx:172-176` "按此类型重跑"）同一交互语法；AbortController 在途取消仍为 P1 优化项（省钱非正确性必需）。

### 5.4 本地路由器（auto 方式的实现，v5 定稿）

**方案比选（用户提出"AI 判断"或"本地路由"，比较后定本地路由）**：

| 候选 | 机制 | 判定 |
| --- | --- | --- |
| AI 预判两段式 | 先发一次小请求判"这段适合通用还是简明"，再按结果发正式请求 | **否**：延迟翻倍（推理模型首字前本就要等 0.5-1 分钟，判错时用户已白等一轮，代价反而最高）、费用+1、失败路径+1。 |
| 单请求自路由 | 一个 prompt 内让模型自行选择按哪种结构输出 | **否**：输出契约分叉为两种结构的并集（测试/闸门复杂化，违背封闭契约惯例）；执行前 UI 无法展示将用哪种方式；要么改现有 reader-explain 模板（违反零改动）要么模板内容三处分叉。 |
| **本地路由器（采用）** | 纯前端表面特征加权规则，立即出结果 | 零请求、零延迟、确定性、可离线单测、符合纯本地优先。弱点是看不见语义歧义——但判错代价不对称且小（见下），语义级判断由事后建议承接（§5.5）。 |

**判错代价分析（本地路由可行的根本理由）**：误入简明解读仍得到改写与说明（不是坏结果）；误入通用解读一键切换即重跑。路由不需要高精度，只需要"大多数时候别让人多按一次"。

**规格**：纯函数 `routeExplainMode(text: string): "general" | "ste"`，新文件 `src/lib/explainRouter.ts`，渲染层本地执行、不发任何请求。
- 特征（材料语言不敏感的表面特征）：平均/最长句长（按 `。！？.!?；;` 切分）、每句逗号/顿号/分号密度、括号嵌套深度、否定词计数（`不/没/无/非/not/no/never/n't`）、施动隐藏标记（`被/by` 及英文被动式）。
- 规则：加权分 ≥ 阈值 → ste，否则 general。权重与阈值以导出常量承载，金样例校准（校准要点：**结构平直的长句不应触发 ste**——句长仅作低权重因子，嵌套/否定/被动密度为主因子）。
- CardDock 标题跟随**解析后**的实际方式（auto → 路由结果）。

### 5.5 事后建议（v5 升格正式功能，P0 交付）

路由是表面特征判断，语义级纠偏交给**已经付费的那次调用**：简明解读结果流式完成后，若机器标记显示明显错配——路由进了 ste 但 `points=0` 且改写与原文几乎一致（文本其实清晰，用户多半更想要概念解释）——面板在答案尾部给一行轻提示："这段更像概念解释，切换到通用解读？"，点击即按 §5.3.4 重跑。纯前端、零额外请求，依赖既有 `<!--ste:…-->` 标记。仅做 ste→general 方向（通用解读模板无标记，且其结果本身总有价值，用户自然切换即可）。

## 6. 多语言适配机制

### 6.1 三个语言角色（概念模型）

| 角色 | 来源 | 用途 |
| --- | --- | --- |
| 界面语言 UI locale | 设置项（P1 引入；P0 固定 zh-Hans） | 控件文案；AI 解释/制卡输出语言的默认值 |
| 材料语言 Material lang | 优先书籍语言标记（`library:setItemLang`）；缺失时模型自检并在 `<!--ste:matLang=xx-->` 报告 | 决定**分析用** pack（对原文找茬按原文语言的规则） |
| 输出语言 Output lang | **默认 = 界面语言**（已拍板；P0 即中文）。P1 起为设置项 `AI 解释语言`，可在设置中改 | 决定**改写用** pack 与全部说明文字语言 |

### 6.2 CLP pack 规格（`electron/ste-profiles/{lang}.json`）

```json
{
  "lang": "zh-Hans",
  "name": "简明中文剖面 v1",
  "derivedFrom": ["ISO 24495-1:2023", "ASD-STE100 Issue 9（仅结构参照，自写蒸馏）"],
  "licenseNote": "original-wording: 本文件全部规则文字为自写，不含 ASD-STE100 规范原文与词典词表",
  "sentence": { "maxChars": 40, "maxClauses": 2, "note": "一句一义；长句必须拆分" },
  "voice": { "preferActive": true, "agentUnknownNote": "施动者不明时显式写'来源未说明'" },
  "lexicon": ["一词一义：同一概念全文用同一个词", "避免文白夹杂与多义成语", "术语首现就地给一句白话定义"],
  "avoid": [{ "bad": "被……所……之", "why": "文白混杂+施动者隐藏" }],
  "rewriteExample": [{ "before": "…", "after": "…" }],
  "source": "docs/design/STE-PLAIN-DECODE-D91.md"
}
```

- 每条 `lexicon/avoid/rewriteExample` 均**人工撰写于该语言**（禁止机翻 STE；禁止复制规范原文）。`derivedFrom` 只写名称与版本。
- P0 内置：`en.json`（句长 20 词、动词形态/主动语态约束，STE 结构自写蒸馏——**服务于英文材料的歧义分析**）、`zh-Hans.json`（如上——分析中文材料 + 改写输出）、`universal.json`（ISO 24495-1 四原则，无量化句长）。
- P1 增补：`ja.json`（やさしい日本語：短句、です・ます、常用漢字、避免片假名术语、一文一義）、`de.json`（Leichte Sprache：每句一信息、避免虚拟式/名词化风格、数字写法规则）。
- **回退链**：精确 locale（zh-Hant-TW→zh-Hans）→ 基础语言（zh）→ `en` → `universal`。解析函数纯函数、可单测。

### 6.3 Prompt 组装管线

- 新 scope：**`reader-explain-ste`**。system 模板 = 任务定义（§4.1，强调完整执行、不判"是否值得"）+ 歧义类别封闭集 + 输出契约（注释标记 + 节序）+ 两个槽位：`{{ANALYSIS_PROFILE}}`（材料语言 pack）与 `{{OUTPUT_PROFILE}}`（输出语言 pack）+ 输出语言指令。模板常量加在 `electron\prompts.js`（中文书写系统指令，输出语言作为参数注入——系统指令语言与输出语言解耦，模型无碍）。P0 中 `{{OUTPUT_PROFILE}}` 恒注入 zh-Hans pack，槽位保留以支持 P1 零改模板升级。
- user 消息拼装沿用现有块格式（`cards.ts:660` 先例）：【选中文本】【上下文】【材料语言】【解读语言】。
- 请求路径完全复用：`promptsAPI.get("reader-explain-ste")` + `aiGateway.chat(...)`。**零新增 IPC、零新表、零 schema 变更**。

### 6.4 与全局 i18n 的合并计划（P1，已拍板：一起做）

多语言 pack 不单独零散上线，与**软件整体界面多语言**合并为同一阶段交付，届时设置面板新增三个语言选项（键名风格实现对齐 GUIDE §4 既有 settings 键约定）：

| 设置项（展示名） | 取值 | 作用 |
| --- | --- | --- |
| 软件语言 | `auto`（跟随系统）/ `zh-Hans` / `en` / `ja` / … | 界面文案 locale；同时是两个 AI 语言选项的默认值来源 |
| AI 解释语言 | `follow-ui`（默认）/ 指定 BCP-47 | 驱动 reader-explain 与 reader-explain-ste 的输出语言（`{{OUTPUT_PROFILE}}` 槽位） |
| AI 制卡语言 | `follow-ui`（默认）/ 指定 BCP-47 | 驱动**制卡 prompt 族**（card-generation/formula/seq/enum/literature/mnemonic/contrast/wording/basic/vocab/occlusion/structure，见 `electron\db.js:1975-2115`）的输出语言——需为该族模板统一增加输出语言槽位，**工作量独立且不小**，届时另立设计稿或将本稿升 v3 承载 |
